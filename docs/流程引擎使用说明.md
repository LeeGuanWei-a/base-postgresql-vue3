## 一、开始之前

### 1.1 前置条件

| 项 | 要求 |
|---|---|
| 数据库 | 已导入 `file-sql/basicdb-vue3.sql`（含全部 `act_*` / `flw_*` / `wf_*` 表） |
| 后端 | `basic-admin-api` 启动成功，端口默认 `8080` |
| 前端 | `web-ui` 已 `pnpm install` 并 `pnpm dev` |
| 账号 | `admin` / `admin123`（超级管理员，建议登录后立即改密） |

后端与流程引擎相关的关键配置在 [basic-admin-api/src/main/resources/application.yml](../basic-admin-api/src/main/resources/application.yml)：

```yaml
flowable:
  async-executor-activate: true    # 异步执行器开启
  database-schema-update: true     # 表结构不一致时自动升级
  idm:
    enabled: false                 # 关闭 Flowable 自带 IDM，用户体系用 sys_user
```

> 因为 `database-schema-update: true`，若库里缺 Flowable 引擎表，启动时会自动补建；
> 但**业务表**（`wf_*`、`tbl_flow_extend_procinst`）不会自动建，必须来自 SQL 脚本。

### 1.2 两个必须知道的概念

| 概念 | 含义 | 存在哪 |
|---|---|---|
| **流程模型（Model）** | 设计器里画的那张流程图，可以反复改 | `act_de_model` / `act_re_model` |
| **流程定义（ProcessDefinition）** | 模型**部署**后的产物，是真正能被发起的东西 | `act_re_procdef` + `act_ge_bytearray` |

**一次部署 = 一个版本**。改了模型并重新部署，版本号 +1；已经在跑的流程实例仍按旧版本走完，不受影响。

## 三、从零跑通一条流程（四步）

下面用一个「请假审批」的例子，串起完整链路。**建议第一次就按这个顺序走，不要跳步**。

### 第 1 步：建流程分类

`流程引擎 → 流程分类 → 新增`

| 字段 | 说明 | 示例 |
|---|---|---|
| 上级分类 | 支持树形；顶级留空 / 选 0 | 顶级 |
| 分类名称 | 显示名 | 人事流程 |
| 分类编码 | **英文唯一标识**，模型靠它归属分类 | `hr` |

> 分类编码（`code`）是模型与分类之间的关联键，不是分类 ID。后面建模型时选的就是这个编码。

### 第 2 步：建流程模型

`流程引擎 → 流程模型 → 新增`

| 字段 | 说明 |
|---|---|
| 模型名称 | 显示名，如「请假审批」 |
| 模型标识 | **英文唯一标识**，如 `leave`。发布流程时后端会拼成 `leave.bpmn` 去匹配流程定义 |
| 流程分类 | 选第 1 步建的分类 |
| 备注 | 选填 |

点「确定」后**会自动跳进流程设计器**（提示"新增成功，即将进入设计器"）。

### 第 3 步：画流程图并保存

在设计器里拖出节点、连线、配置审批人（详见[第四章](#四流程设计器详解)、[第五章](#五节点配置审批人与授权功能)），然后点**保存流程**。

系统做两件事：

1. `saveModel`：把 BPMN XML 写回模型，**保存前会做"流程合规校验"**（例如：遗漏审批人、连线不合法）。校验不通过会弹窗列出全部问题清单，按提示改完再存。
2. `deployModel`：**保存成功后立即自动部署**（保存即部署），然后提示"保存并部署成功"并返回模型列表。

> 如果出现"保存成功，但自动部署失败"，模型仍是已保存状态，可以回列表手动部署。

保存并部署后，列表里该模型的**状态**变为：

| 状态 | 含义 | 可执行操作 |
|---|---|---|
| 未部署 | 只存了模型，还不能发起 | 设计、删除 |
| 已部署 | 可以发起新流程 | 设计、停用、删除 |
| 已挂起 | 不能发起新的，**已发起的流程不受影响** | 设计、激活、删除 |

### 第 4 步：发起并审批

- 发起：`流程模型` 列表里对已部署的模型点发起，或走「测试启动流程」页选模型 → 填流程变量（JSON）→ 发起。发起成功后可拿到 `procInsId`（流程实例 ID），业务系统应保存它作为与流程的关联依据。
- 审批：切到被指派的账号，进 `我的待办`，点「详情」或直接点审批按钮。

## 四、流程设计器详解

设计器基于 **bpmn-js**，页面为 `/workflow/model/design`（`views/workflow/model/design.vue`），并挂载了两个自定义插件：

- 自定义 Palette（左侧元素面板）
- 自定义 ContextPad（选中元素后的快捷菜单，其「Append task」创建的是 **UserTask（用户任务）** 而不是抽象 Task）

### 4.1 画布基本操作

| 操作 | 方式 |
|---|---|
| 添加节点 | 从左侧面板拖到画布 |
| 连线 | 选中节点 → 拖动节点边缘的箭头到目标节点 |
| 修改属性 | 点击节点，右侧属性面板出现对应页签 |
| 删除 | 选中后按 Delete，或右键 |
| 缩放 / 平移 | 鼠标滚轮 / 按住空白处拖动 |

### 4.2 节点与连线类型

| 元素 | 用途 |
|---|---|
| 开始事件（StartEvent） | 流程唯一入口。**必须配置表单**（发起人在这里填单） |
| 用户任务（UserTask） | 需要人审批的节点，是使用频率最高的元素 |
| 排他网关（ExclusiveGateway） | 按条件走**其中一条**分支（例如：金额 > 5000 走总经理） |
| 并行网关（ParallelGateway） | 分支同时进行，全部到达后才继续 |
| 包含网关 / 事件网关 | 更复杂的汇聚/事件驱动场景 |
| 服务任务 | 系统自动执行（本项目需自行配置委托表达式） |
| 子流程 / 调用活动 | 流程内嵌或调用另一条流程 |
| 边界事件 | 挂在用户任务/子流程/调用活动**边界**上，做"异步分流"。本项目支持 8 种类型（timer/message/signal/error/escalation/cancel/compensation/conditional），详见 [§4.6](#46-边界事件boundary-event-详解) |
| 结束事件 | 流程终点 |

### 4.3 连线条件（网关分支）

选中**从网关出发的连线**，右侧会出现「条件」页签，可选三种写法：

| 类型 | 写法 | 例子 |
|---|---|---|
| 表达式（expression） | `${...}` | `${days > 3}` |
| 内联脚本（inlineScript） | 选脚本语言后写脚本 | — |
| 外部脚本（externalScript） | 写资源地址 | — |

另外可以设**默认流（default flow）**：所有条件都不命中时走这条。

> 表达式里能引用的变量 = 发起时填的「流程变量」+ 审批过程中写入的变量。
> 例如发起时传 `{"days":5}`，则 `${days > 3}` 命中。

### 4.4 其他可用配置

| 配置项 | 位置 | 说明 |
|---|---|---|
| 表单标识 | 元素属性 → 表单 | 给节点绑定业务表单（见第六章） |
| 执行监听器 / 任务监听器 | 元素属性 → 监听器 | 支持类、表达式、委托表达式、脚本四种 |
| 多实例 | 元素属性 → 多实例 | 会签/或签、集合、元素变量、完成条件 |
| 流程变量 localScope | 元素属性 | 控制变量作用域 |

### 4.5 常用扩展属性（节点上落库的样子）

设计器把面板上的开关写成 BPMN 扩展属性，运行时由引擎缓存读取（不产生额外库查询）：

| 扩展属性 | 对应面板项 |
|---|---|
| `flowable:IdmPermission` | 授权功能（JSON 数组文本，见第五章） |
| `flowable:IdmAssignee` | 分配人员（单个，身份存储） |
| `flowable:IdmCandidateUsers` | 候选人员 |
| `flowable:IdmCandidateGroups` | 候选角色 |
| `flowable:IdmAuthority` | 固定值里勾选的角色 |
| `flowable:IsSkip` | 处理人配置 → 自动跳过 |
| `flowable:IsNullSkip` | 为空跳过 |
| `flowable:IsExamined` | 审批配置（同一处理人只需审批一次） |
| `flowable:IsRoleReplace` | 交替配置（连续节点处理人相同则跳过） |
| `flowable:IsRevoke` | 强制撤回多实例节点存在已审的情况 |
| `flowable:IsUserScreen` / `flowable:IsOrgScreen` / `flowable:IsDeptOrOrg` | 人员筛选相关 |
| `flowable:BoundaryType` / `flowable:BoundaryTimerDuration` / `flowable:BoundaryErrorCode` 等 | 边界事件扩展属性（见 §4.6） |

### 4.6 边界事件（Boundary Event）详解

边界事件是挂在某个**活动**（UserTask / SubProcess / CallActivity）的**边界**上的"小钩子"。当这个活动正在执行时，**只要条件命中**（时间到了 / 收到消息 / 收到信号 / 抛出错误等），流程就会从**这个钩子的出向连线**流走——**和正常审批出向同时存在**。

这是和"主审批出向"的本质区别：**主出向是"审完才走"**，边界事件是"**还没审完就被另一件事打断**"。

#### 4.6.1 8 种类型在画什么、做什么

设计器 palette 把所有 8 种都画成同一个"中间/边界事件"图标——具体类型要选中后**在右侧「边界事件」分组的下拉框里选**（拖出后默认是"未指定"）。每种类型的差异由它的 `eventDefinitions[0].$type` 决定。

| 类型 | 何时被触发 | 触发后做什么 | 典型场景 | 是否能挂 UserTask |
|---|---|---|---|---|
| **定时器（timer）** | 时间到（duration/cycle/date） | 沿出向连线流走 | 审批 24 小时没审，自动走超时分支（催办 / 自动通过 / 转他人） | ✅ |
| **消息（message）** | 外部系统调 `messageEventReceived(name, execId)` | 沿出向连线流走 | 等另一个流程发来的"审核完成"消息，**收到才继续** | ✅ |
| **信号（signal）** | 外部调 `signalEventReceived(name)` | 沿出向连线流走 | 全局广播：某条新闻"产品下线"，所有挂着该 signal 边界的流程同时响应 | ✅ |
| **错误（error）** | ServiceTask/JavaDelegate 抛 `BpmnError(errorCode)` | 沿出向连线流走 | ServiceTask 调外部接口超时 / 业务校验失败，把活动带进"出错分支"（不影响主流程） | ✅ |
| **升级（escalation）** | 节点抛 `BpmnEscalation(code)` | 沿出向连线流走 | 业务侧"轻度异常"——和 error 类似但语义更轻（不视作失败） | ✅ |
| **取消（cancel）** | 事务/外部取消触发 | 沿出向连线流走 | 发起人撤销申请 → 触发挂在子流程边界上的 cancel 边界 → 进入"撤销后处理"分支 | ⚠️ **仅在 transaction / call activity 子流程边界有效**，挂 UserTask 不会触发 |
| **补偿（compensation）** | 外部 throw compensation | 沿出向连线流走 | 流程回滚——"前面已办的事需要撤销时"，触发补偿活动 | ✅（但需与 throw compensation 配合） |
| **条件（conditional）** | 条件表达式求值为 true | 沿出向连线流走 | `${amount > 10000}` 当金额超阈值直接升级到特殊节点 | ✅ |

#### 4.6.2 画一个 boundary event 的步骤

1. 从左侧 palette 拖出**中间/边界事件**图标；
2. 放到**目标活动的边框上**（不是中间——放中间就是中间事件了，行为完全不同）；
3. 选中后，**右侧「边界事件」分组**里会看到一个下拉框「**事件类型**」——选你需要的（定时器 / 消息 / 信号 / 错误 / 升级 / 取消 / 补偿 / 条件）；
4. 选完类型，对应的**配置面板**（时长 / 错误码 / 信号 code 等）会出现在下方，填一下必填项；
5. 画一条**出向连线**连到你想去的节点（这条线是 boundary 触发后流程走向的地方）；
6. **点保存流程**——保存前会自动校验，没填的必填项会列在弹窗里。

> **取消活动（cancelActivity）** 是每个 boundary 都可以开关的：
> - 勾上（默认）：触发时**中断宿主活动**（用户任务被中断，不再走主出向）；
> - 去掉：触发时**不中断宿主活动**（用户任务继续等审批，boundary 流走的是另一条并行分支）。
>
> 比如"24 小时没审就催办"通常**不勾**——催办和正常审批同时存在，催办完用户还是要去审批。

#### 4.6.3 中断 vs 非中断

bpmn-js 设计器在调色板里把"中断 / 非中断"画成两个独立图标。**本项目当前仅支持"中断"型**——非中断边界事件**暂未在 `BruceBoundaryEventJsonConverter` 注册**，需要的话后续加上。

#### 4.6.4 后端触发接口（runtime 调用）

本项目把"信号/消息/错误/取消"4 种**外部可触发的**类型封装成了接口，让业务系统不写 Java 代码也能驱动流程：

| 接口 | 路径 | 权限 |
|---|---|---|
| 触发信号 | `POST /workflow/boundary/signal` | `workflow:boundary:trigger` |
| 触发消息 | `POST /workflow/boundary/message` | `workflow:boundary:trigger` |
| 触发错误（标记变量） | `POST /workflow/boundary/error` | `workflow:boundary:trigger` |
| 触发取消（删除子流程） | `POST /workflow/boundary/cancel` | `workflow:boundary:trigger` |
| 查询当前实例的 boundary 列表 | `GET  /workflow/boundary/list/{procInsId}` | `workflow:boundary:query` |

请求体（统一为 `WfBoundaryTriggerBo`）：

```json
{
  "procInsId": "a1b2c3d4-...",
  "eventCode": "approval-passed",
  "comment": "由业务系统在订单完成后回调",
  "variables": { "amount": 8500 }
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `procInsId` | ✅ | 流程实例 id（来自发起时接口返回） |
| `eventCode` | signal/message/error 必填 | 信号名 / 消息 id / 错误码（对应 boundary 上配的 `signalCode` / `messageId` / `errorCode`） |
| `comment` | ❌ | 触发原因，写入流程变量 `boundaryTriggerComment` |
| `variables` | ❌ | 附加流程变量 |

> 错误边界**没有"从外部直接抛 BpmnError"的标准接口**——`RuntimeService` 不支持。`triggerError` 的实现是**在流程变量里写错误码标志**，由**业务侧的 ServiceTask / JavaDelegate 监听这个变量后调用 `execution.bpmnError(code)`** 抛出。约定变量名 `boundary_error`，与流程 status（同时写成 `boundary_error`）一致。
>
> 定时器（timer）和条件（conditional）**不需外部触发**——引擎自己到时间 / 表达式自己求值。

#### 4.6.5 流程变量约定

触发成功后，**`processStatus` 流程变量**会被改写成 `boundary_<type>`（如 `boundary_signal` / `boundary_error`），用于列表筛选"被 boundary 触发的流程"。

流程**正常结束后**，`GlobalEventListener` 会把它归一化回 `completed`（见 §4.6.6）。

#### 4.6.6 全局监听与状态收尾

`extend-flowable` 里的 `GlobalEventListener` 监听 `PROCESS_COMPLETED`，流程结束时：

| 触发前 status | 触发后 status |
|---|---|
| `running` | `completed`（普通流程正常结束） |
| `boundary_<type>` | `completed`（被 boundary 触发走完的流程，状态归一化） |
| `canceled` | 保持 `canceled`（已是终态） |

#### 4.6.7 保存前的合规校验

`WfProcessComplianceValidator` 在保存流程时会一并校验 boundary，**不通过的会被 `design.vue` 的弹窗列出来**（不会自动保存）：

| 规则 | 错误信息（大致） |
|---|---|
| boundary 必须挂在某个活动上（`attachedToRef`） | `边界事件[<name>] 没有挂在任何活动上...` |
| boundary 必须有具体事件定义 | `边界事件[<name>] 没有配置事件定义...` |
| timer 必须配 duration/cycle/date | `定时器边界事件[<name>] 没有配置时长...` |
| error 必须配 errorCode | `错误边界事件[<name>] 必须配置 errorCode...` |
| cancel 不能挂 UserTask | `取消边界事件[<name>] 仅在 transaction / call activity 子流程边界有效...` |
| 同一宿主上同类型 boundary 重复 | `宿主活动[<id>] 上挂了 N 个同类型（<type>）的边界事件...` |

> 这些只是**业务侧经验规则**（不是 BPMN 规范的硬性要求）。比如 "同宿主同类型 boundary 重复" Flowable 不会拦，但运行期行为未定义，所以校验器给你个 warning 让你合并。

#### 4.6.8 与现有"超时不审批"实现的对比

项目里之前有个**空的骨架** `ProcessDueTimeListener`（`extend-flowable/src/main/java/com/basic/flowable/listener/ProcessDueTimeListener.java`），本意是"通过监听器实现超时自动处理"——但代码里只是 `System.out.println`，**没接任何业务**。

> **现状**：通过 `ProcessDueTimeListener` 实现超时**没接通**，业务上"超时不审批"目前要靠人工催办。
>
> **推荐做法**：用 **timer 边界事件**替代：
> 1. 在需要超时的 UserTask 边框上挂 timer 边界，配置 `PT24H`；
> 2. 出向连到一个"超时处理"节点（自动通过 / 转给上级 / 结束流程 三选一）；
> 3. 引擎自带的 Job Executor 会按 duration 到点触发，不需要额外监听器。

### 4.7 流程替换（运行中实例迁移到新流程定义）

#### 4.7.1 这是什么

有时候人事变动 / 业务模式变更后，**已经发起的流程**需要换走新流程定义——比如：
- 旧流程在 UserTask `Activity_audit_first` 上配的审批人 A 离职了，新版本把该节点审批人换成 B
- 旧流程上某个 UserTask 删了，新流程调整了分支结构
- 业务部门整体重写流程图，要求历史在途流程按新版本继续走

"流程替换"就是把一条**正在跑**的流程实例**整条迁到新流程定义上**继续跑——新流程沿用旧流程的启动人 / businessName，复制历史意见和附件，可选地镜像推进若干节点，最后废除旧流程。

#### 4.7.2 提供的接口

| 接口 | 路径 | 权限 | 用途 |
|---|---|---|---|
| 触发替换 | `POST /workflow/process/migrate/replace` | `workflow:process:migrate` | 事务内执行，失败回滚 |
| 校验参数 | `POST /workflow/process/migrate/validate` | `workflow:process:migrate` | 不实际执行 |

Service：`IWfProcessMigrateService.replaceProcessInstance(plan)`，抛出 `WfProcessMigrateException` 表示失败。

#### 4.7.3 替换计划 WfProcessMigratePlan

```java
// 推荐写法：不传 advanceSteps，自动按旧流程历史镜像
WfProcessMigratePlan plan = WfProcessMigratePlan.builder()
    .oldProcInsId("a1b2c3...")                  // 必填：旧流程实例 id
    .newProcessDefinitionKey("payOld")          // 必填：新流程定义 key
    .startVariables(Map.of("st", 0))            // 选填：启动变量
    .copyComments(true)                          // 选填：是否复制历史意见，默认 true
    .copyAttachments(true)                       // 选填：是否复制附件，默认 true
    .reason("人事变动：A 离职，由 B 接替")         // 选填：会作为一条新意见写入新流程
    .businessCallback((oldId, newId) -> {        // 选填：业务表更新回调（旧→新）
        // 业务侧更新自己业务表里的 procInsId 字段
        // 不要在这里发消息、调外部接口、起新流程
    })
    .build();
String newProcInsId = wfProcessMigrateService.replaceProcessInstance(plan).getNewProcInsId();

// 仅当需要"新流程比旧流程走得更远"时才手动指定节点（走模式 B）
// .advanceSteps(List.of(
//     WfProcessMigratePlan.AdvanceStep.skip("Activity_audit_first"),
//     WfProcessMigratePlan.AdvanceStep.skip("Activity_audit_second", Map.of("flag", 0))))
```

#### 4.7.4 镜像推进的两种模式

替换时"新流程要走到哪一步"由**镜像推进**决定，有两种模式：

**模式 A：自动镜像（推荐，不传 `advanceSteps`）**

后端读旧流程的**已完成 userTask 历史**（`act_hi_actinst` 里 `activityType='userTask'` 且已结束的记录，按结束时间升序），按同样顺序在新流程上逐个 `complete`，最终落点与旧流程**完全等价**：

- 旧流程走过哪些节点，新流程就走哪些节点
- 会签节点按旧流程**实际完成的次数**推进（旧流程会签过了 2 个人，新流程也推 2 次）
- 旧流程里因条件分支没走到的节点，不会被推
- 节点处理人沿用旧流程该节点的实际 `assignee`，保证历史记录一致

**这是最不会出错的方式** —— 不需要人判断该勾哪些节点。

**模式 B：手动指定 `advanceSteps`**

适用于"希望新流程比旧流程走得更远/更近"的场景。传了 `advanceSteps` 时：

- 后端会按**新流程图的真实走向顺序**（用 `sequenceFlow` 从 startEvent 做 BFS 算出来的）重排这些节点，**不是按传入顺序**
- 原因：bpmn 文件里元素的声明顺序是 bpmn-js 的**画图顺序**，不等于流程走向顺序。若按声明顺序推，先推靠后的节点会因"新流程还没走到那里"而查不到 task，被静默跳过
- 会签节点会自动循环推进，直到该 `taskDefinitionKey` 没有活动 task 为止

> ⚠️ 手动模式下请只勾选**旧流程已经走过**的节点。把"旧流程当前停留的节点"勾上会把新流程推**过**该节点（过冲）。迁移页的表格里用"已走过/未走过"标签标出每个节点在旧流程里的状态。

#### 4.7.5 内部执行步骤

整个替换在**单一事务**内执行，**任何一步失败整体回滚**：

1. 校验旧流程存在且未结束
2. 校验新流程定义存在且未挂起
3. 启动新流程（沿用旧流程的启动人 / processName / appSn）
4. 镜像推进（见 §4.7.4：未传 `advanceSteps` 时自动按旧流程历史镜像）
5. 复制历史意见（按 procInsId 重写，每条加 `[从旧流程 xxx 复制]` 前缀）
6. 复制附件（按 processInstanceId 重新插入）
7. 写一条"流程替换：xxx（旧流程 yyy 已废除）"意见到新流程
8. 执行 `businessCallback`，让调用方更新业务表
9. 废除旧流程（soft delete：历史保留，但状态置废除）

> 第 9 步调的是 `WfTaskServiceImpl.abolishProcess`，它**只读 `WfTaskBo.procInsIdList`**（不看 `procInsId`），传入时必须把实例 id 放进 `procInsIdList` 才会真正废除。

**关于镜像推进的操作人身份**：推进新流程节点时会走 `WfTaskServiceImpl.complete`，其中包含 `WfTaskAuthService.checkOperateAuth`（校验"这个任务是不是你的"）。迁移是**代表他人推进**的系统行为——当前登录用户通常不是那些节点的处理人/候选人（例如登录的是管理员，而待推进节点候选人是别人），因此迁移内部通过 `WfTaskAuthService.callAsSystem(...)` 以**系统身份**调用，跳过该校验。

- 该标记是 `ThreadLocal`，**只能由服务端代码设置**，HTTP 请求体无法设置，不构成越权入口
- 写入历史的"办理人"按此优先级解析：步骤指定的处理人 → 任务当前 assignee → 任务的**第一位候选人** → 旧流程发起人（兜底），保证新流程历史里的办理人不是空的

#### 4.7.6 HTTP 接口请求体

```json
{
  "oldProcInsId": "a1b2c3...",
  "newProcessDefinitionKey": "payOld",
  "startVariables": { "st": 0 },
  "copyComments": true,
  "copyAttachments": true,
  "reason": "人事变动：A 离职，由 B 接替",
  "advanceSteps": []
}
```

> `advanceSteps` **留空或省略**即走"自动镜像"（推荐，见 §4.7.4）。
> 只有需要手动指定推进节点时才传，例如：
> ```json
> "advanceSteps": [
>   { "taskDefinitionKey": "Activity_audit_first" },
>   { "taskDefinitionKey": "Activity_audit_second", "variables": { "flag": 0 } }
> ]
> ```

> HTTP 入口**不暴露 businessCallback**——业务回调只能通过 Service API（注入 lambda）传入。
> 如果是纯流程引擎层调用（无需更新业务表），用 HTTP 入口即可。

#### 4.7.7 不能做什么

- 不能跨 modelKey 映射变量 / 表单（旧流程的流程变量不会自动迁到新流程）
- 不能"部分迁移"——要么全换，要么不换
- 不能迁移"草稿"状态（没实例可换）
- 不能迁移"已结束"流程
- 不在事务内做"发消息 / 调外部接口 / 起新流程"——这些放外层

#### 4.7.8 业务侧接入示例

```java
// 业务侧定时任务：扫出"审批人 A 离职影响到的运行中流程"
List<BusinessApply> affectedList = businessApplyMapper.selectRunningWithAssignee("A");
for (BusinessApply apply : affectedList) {
    WfProcessMigratePlan plan = WfProcessMigratePlan.builder()
        .oldProcInsId(apply.getProcIncId())
        .newProcessDefinitionKey("applyV2")
        .reason("审批人 A 离职，自动迁到 V2 流程（审批人 B）")
        // 不传 advanceSteps：自动按旧流程已走过的节点镜像，落点与旧流程一致
        // 业务表更新：把 procIncId 指向新流程
        .businessCallback((oldId, newId) -> {
            apply.setProcIncId(newId);
            businessApplyMapper.updateById(apply);
        })
        .build();
    try {
        wfProcessMigrateService.replaceProcessInstance(plan);
    } catch (WfProcessMigrateException e) {
        log.error("[人事变动迁移] 失败 applyId={} err={}", apply.getId(), e.getMessage(), e);
    }
}
```

#### 4.7.9 与 §4.6 边界事件的关系

- **边界事件**：流程**运行中**，事件触发使流程从某条**支线**流走
- **流程替换**：流程**运行中**，把整条实例迁移到**新流程定义**继续跑

两者正交。可以同时用：边界事件挂"超时转他人"、流程替换用于"全局人事变动"。

### 4.8 流程数据清盘（一键清空，危险操作）

> ⚠️ **这是本系统唯一的"不可恢复"操作**。会把流程相关的全部数据物理删除。
> 用途仅限：开发/测试环境重置、交付前的环境清理。**生产环境请勿使用。**

#### 4.8.1 入口与二次确认

`流程引擎 → 流程中心`，右上角红色按钮【**清空全部流程数据**】。

点开后是**两步确认**，中间不是普通弹窗：

1. **先给你看账单**：弹窗会调 `/workflow/process/clear/preview` 展示
   "运行中实例数 / 历史实例数 / 部署数 / 模型数" + 10 张主要业务表的行数
2. **再要求手打短语**：必须手动输入 `清空流程` 四个字，输错则【确认清空】按钮保持禁用

后端同样校验这个短语（`IWfProcessClearService.CONFIRM_TEXT`），所以即使有人直接调 API 也得带对文字。

权限串：`workflow:process:clearAll`（菜单与权限数据已包含在
[file-sql/basicdb-vue3.sql](../../file-sql/basicdb-vue3.sql) 中，随库导入即可）。
**建议只授予超管**。

#### 4.8.2 清除范围

分 6 步执行，**整体在一个事务内，全有或全无**：

| 步骤 | 做什么 | 为什么必须这么做 |
|---|---|---|
| 1 | 运行中实例：`runtimeService.deleteProcessInstance` **强制终止** | 必须走引擎 API——它会一并清理执行树、任务、变量、身份链接、定时器作业、事件订阅，并正确维护历史。直接 DELETE 表会留下孤儿作业与引擎内存态 |
| 2 | 历史实例：`bulkDeleteHistoricProcessInstances` 分批删（每批 500） | 单次调用有数量上限 |
| 3 | 部署：`deleteDeployment(id, true)` 级联删 | 必须走引擎 API——它会驱逐**引擎内部**的流程定义缓存 |
| 4 | 模型：`deleteModel(id)` | 同上 |
| 5 | **应用级定义缓存**：`customDeploymentCache.clear()` | 项目自研的 `CustomDeploymentCache` **没有注册进 Flowable 引擎**（全项目无 `setProcessDefinitionCache` 调用），只是 `WfBpmnModelServiceImpl` 自用的缓存。引擎删部署**不会**连带清它，必须手动清，否则清完还能从内存读到已删除的定义 |
| 6 | 残留表 + 业务表：动态 `DELETE FROM`，先过滤存在性 | 前 5 步通常已把引擎表清空，这步是兜底回收孤儿行，并清业务表 |

#### 4.8.3 明确**不会**删除的东西

| 保留项 | 原因 |
|---|---|
| `act_ge_property` | 引擎 schema 版本与自增 id 计数器，删了引擎起不来 |

| `act_de_*` | flowable-ui-modeler 的表，本项目不使用，且部分环境里不存在 |

#### 4.8.4 清完之后要做什么

流程**分类、表单、模型、流程定义全被清掉**，所以顺序不能乱：

1. `流程分类 → 新增`（**没分类建不了模型**）
2. `流程模型 → 新增` → 进设计器画图 → 保存（保存即部署）
3. `表单管理 → 新增`（如果流程要挂表单）
4. 之后就能正常发起流程

> **`flw_expression`（表达式字典）也被清空**——如果你依赖里面的表达式（如审批人筛选的 `${...}`），需要重建。

#### 4.8.5 排查记录：为什么不能用 `WHERE 1=1` 绕过

项目在 `MybatisPlusConfig` 注册了 `BlockAttackInnerInterceptor`，它会拦截"没有 WHERE 的 DELETE"（报 `Prohibition of full table deletion`）。清盘 Mapper 上是这样处理的：

```java
@InterceptorIgnore(blockAttack = "true")   // MyBatis-Plus 官方忽略机制，只作用于本方法
int deleteAllFromTable(@Param("tableName") String tableName);
```

**不要试图用 `DELETE FROM t WHERE 1=1` 绕过**——MP 3.5.1 的 `BlockAttackInnerInterceptor.fullMatch()` 会专门判断 `EqualsTo` 且左右字面量字符串相等，`1=1` 正好命中，照样被拦。

**表名安全**：表名不能用预编译参数，所以做了三重校验——硬编码白名单 → 正则 `^[a-z_][a-z0-9_]*$` → `information_schema` 查库内是否存在。用户输入碰不到表名。

#### 4.8.6 表清单为什么要先查存在性

不同环境里 Flowable 的辅助表不一定都建了（例如事件注册表的 `flw_event_*`、批处理表 `flw_ru_batch*`）。

PostgreSQL 有个特性：**一条语句失败会让整个事务进入 aborted 状态**，后续语句全部报错。所以必须先筛出真实存在的表再删，否则遇到一张不存在的表就会让整个清盘失败。日志里会打印跳过的表：

```
[process-clear] 以下表在当前库中不存在，已跳过：[...]
```

如果这行**没出现**，说明 46 张表全部存在且都被清了。

## 五、节点配置：审批人与授权功能

点击一个**用户任务**节点，右侧面板从上到下依次是：

### 5.1 顶部开关（人从哪来）

| 面板项 | 含义 | 建议 |
|---|---|---|
| 是否通过组织架构筛选 | 开启后，绑定的人员/表达式按所选组织筛选 | 多组织场景开启 |
| 筛选方式（部门 / 组织架构） | 二选一，近似单选 | 单公司用"部门" |
| 根据发起人所在部门筛选 | 只筛选与发起人同公司/部门的人 | 按需 |
| 是否强制撤回多实例节点存在已审的情况 | 允许撤回"已有人审但没审完"的会签节点 | 按需 |
| 审批配置（是否） | 开启后同一处理人处理相同节点只需一次 | 避免重复审批时开 |
| 交替配置（是否） | 开启后**两个连续节点的处理人相同则自动跳过** | 减少无意义审批 |
| 处理人配置（自动跳过） | 开启后连续节点处理人相同自动跳过 | 同上 |
| 为空跳过 | 处理人为空时跳过该节点 | 表达式可能算出空值时开 |

### 5.2 审批人来源：两个页签

左侧页签用**固定值**还是**身份存储**，决定审批人怎么算：

| 页签 | 适用场景 | 配置方式 |
|---|---|---|
| **固定值** | 流程可适用于多个公司，审批人用**表达式**动态求值 | 「分配人员」填表达式，如 `${starter}`、`${deptLeader}` |
| **身份存储** | 流程只给单个公司用，审批人**直接选人/选角色** | 「分配」三选一：候选人员 / 候选角色 / 分配给流程发起人 |

**身份存储**的「分配」有两种（界面呈现时）：

| 分配方式 | 效果 |
|---|---|
| 候选人员 | 任务进入**待签收**，候选人之一先签收（claim）再办理 |
| 分配给流程发起人 | 直接把任务派给发起人 |

> 固定值里的表达式可以写成引擎表达式（`${...}`），也可以引用「表达式管理」里维护的字典项
> （`flw_expression` 表，见[第二章菜单总览](#二菜单总览)）。

### 5.3 授权功能（决定审批时有哪些按钮）

这是**最关键的一项**，勾了什么，审批人就看到什么按钮。可选值：

| 值 | 按钮文案 | 含义（界面悬浮提示为准） |
|---|---|---|
| `complete` | 同意 | 通过并流转到下一节点 |
| `reject` | 驳回 | **直接结束流程**（状态标记为「已驳回」），发起人需重新发起 |
| `return` | 退回 | 退回到**指定节点**，流程继续流转 |
| `transfer` | 转办 | 把任务转给他人处理，**处理完不再回到自己** |
| `delegate` | 委派 | 委派他人处理，**处理完回到自己确认** |
| `copy` | 抄送 | 允许该节点在审批时抄送给他人（**不是独立按钮**，随同意/驳回一起提交） |
| `mulitiSequentialUnComplete` | 会签回退 | **顺序会签专用**：回退到本节点上一位已处理的审核人 |
| `addSignBefore` | 前加签 | 在当前节点前插入审批人（可多选） |
| `addSignAfter` | 后加签 | 在当前节点后插入审批人（可多选） |
| `stop` | 终止 | 结束整个流程（历史记录、审批意见、表单数据保留） |

> 上述候选值来源有两个：
>
> 1. **字典** `wf_process_permission`（`sys_dict_data`，`dict_value` 列就是上表的 `值`）—— 可在「系统管理 → 字典管理」里维护；
> 2. **前端兜底** [`UserTask.vue` 的 `permissionOptions`](web-ui/src/plugins/package/penal/task/task-components/UserTask.vue) —— 字典没配置时使用，避免复选框出现空白。
>
> 任何一处加了新值（如 `skipUserTask`），三个地方（这里、设计器字典/兜底、前端 [`actionMeta.js`](web-ui/src/views/workflow/process/components/actionMeta.js)）都要同步。

**为什么我的审批按钮不见了？** 两个条件必须同时满足：

1. 节点「授权功能」勾了对应项（后端从 `idmPermission` 读出，接口返回 `permissionJson`）；
2. 当前用户所属角色有对应菜单权限（见[第十章](#十权限对照表)）。

> 历史版本里「终止 / 前加签 / 后加签」不属于授权功能，**当前版本已并入**，勾选才出现。这意味着存量模型（升级前部署的）需要重新打开勾选后重新部署，新发起的流程才会有这三个按钮。

### 5.4 多实例：会签 / 或签

当节点选了候选人员或候选角色（或使用固定值表达式）时，面板下方出现「多实例审批方式」：

| 选项 | 实际含义 | 底层 |
|---|---|---|
| 无 | 普通单实例节点 | — |
| 会签（需所有审批人同意） | 所有人都要处理，全部通过才继续 | ParallelMultiInstance |
| 或签（一名审批人同意即可） | 任一人处理即完成 | ParallelMultiInstance + 完成条件 |

再配合「**顺序审批**」开关：

- **开启顺序审批**的会签 = 依次轮流审批，此节点才会出现「**会签回退**」按钮的生效条件之一；
- **关闭**则是并行会签，所有人同时收到任务。

> 顺序会签节点的「会签回退」还需在授权功能里勾选 `mulitiSequentialUnComplete`，两个条件都满足按钮才出现。
> 会签用的元素变量要与候选人员表达式的变量一致（面板上有对应提示）。

## 六、表单：设计、绑定与生效时机

本项目的业务表单基于 **vForm3（可视化表单设计器）**，数据以 JSON 存放在 `wf_form.content`。

### 6.1 画一张表单

`流程引擎 → 表单管理 → 新增`（填：表单名称、表单编码、表单类型、表单分类）→ 列表点「**设计表单**」进入 `/workflow/form/design`：

1. 从左侧控件库拖控件到画布（输入框、下拉、日期、附件等）；
2. 右侧配置控件属性（字段名、必填、校验）；
3. 点「**保存表单**」。

设计器工具栏保留：清空设计器、预览表单、导入 JSON、导出 JSON（语言切换、外链、内置模板、导出代码均已关闭）。

> 保存后会弹提示：**流程审批读取的是「部署时的表单快照」，本次修改需要重新部署流程后才对新实例生效。**

### 6.2 把表单绑到节点

回到 `流程模型 → 设计`，选中节点（开始事件、用户任务等），右侧「表单」页签的「**表单标识**」下拉里选表单 → 保存。

- 绑定结果是节点上的 `formKey`；
- **开始事件必须绑定表单**：发起人就是在那里填单的；
- 用户任务绑定表单后，审批弹窗里会渲染该表单（只读回显 + 可编辑填写）。

### 6.3 表单数据的流转

> ⚠️ **本节是脚手架实现的「兜底」说明,不是推荐做法。生产项目请按 6.3.1 的正确架构改造。**

#### 6.3.1 重要：业务数据应存业务表，不要塞进 wf_task_form

`wf_task_form` 是流程引擎的「**节点表单**」通用表，设计上是**预留**给脚手架快速跑通流程用的——

**正确架构应该是：**

- **业务数据**（请假天数 / 报销金额 / 出差原因 / 附件 ID 等）→ **存到各自的业务表**
  （例如 `sys_leave` / `sys_expense_report` 等），用普通列、`NOT NULL` 约束、外键、索引，
  业务查询 `SELECT * FROM sys_leave WHERE ...` 直接走索引
- **业务表与流程的关联**用 `proc_ins_id` 字段做「软关联」
- **`wf_task_form` 表只放流程视角需要的元数据**：
  节点 ID、任务 ID、当时填写的**控件名清单**（`activityId` / `taskId` / `userId` / 控件路径），
  或者干脆**只放 `proc_ins_id` + `form_id` + 业务表主键 ID 的引用**，
  **不要把业务字段值塞进 JSON 文本**

**为什么不能把业务数据存到 `wf_task_form`：**

| 问题 | 影响 |
|---|---|
| `form_content` 是 JSON 文本，业务字段无类型约束 | `days` 字段理论上能存 `"abc"`，数据库不会拒绝 |
| 无法用 B-tree 索引，业务查询全走 `jsonb ->> '字段'` 解析 | PG 虽能建 GIN 索引，但 SELECT 性能比普通列差一个数量级 |
| 无法 JOIN | 业务表（请假/报销）与流程表（用户/部门）JOIN 困难，关联查询全卡在 JSON 解析上 |
| 数据膨胀快 | 一条流程 5 个节点 = 5 行 JSON，业务上只算 1 条数据；表会迅速变大 |
| 业务流程结束后，数据还赖在 `wf_task_form` | 这表是「节点级」粒度，大部分行是历史垃圾，清理困难 |
| 业务报表/聚合查询全部要解析 JSON | `SELECT AVG((form_content->>'days')::int) FROM wf_task_form WHERE ...` |

**生产项目改造示例（脚手架之外的代码，需自行实现）：**

```java
// ❌ 脚手架的兜底做法（把所有控件值塞进 JSON）
WfTaskForm wfTaskForm = new WfTaskForm(taskId, formDataJson, procInsId, ...);
wfTaskFormService.saveFormData(wfTaskForm);

// ✅ 推荐做法：业务数据落业务表，流程表只存关联
LeaveRequest leave = new LeaveRequest();
leave.setUserId(userId);
leave.setDays(formData.getInteger("days"));      // 直接存到业务表
leave.setReason(formData.getString("reason"));   // 直接存到业务表
leave.setProcInsId(procInsId);                    // 软关联
leaveService.save(leave);

WfTaskForm wfTaskForm = new WfTaskForm();
wfTaskForm.setTaskId(taskId);
wfTaskForm.setProcInsId(procInsId);
wfTaskForm.setFormId(formId);
wfTaskForm.setActivityId(activityId);
wfTaskForm.setUserId(userId);
// 不再 setFormContent
wfTaskFormService.saveFormData(wfTaskForm);
```

**业务查询对照：**

```sql
-- ❌ 错的（走 JSON 解析，无索引，慢）
SELECT * FROM wf_task_form
WHERE form_content::jsonb ->> 'status' = 'approved';

-- ✅ 对的（走业务表普通列，带索引，快）
SELECT * FROM sys_leave
WHERE approval_status = 'approved';
```

#### 6.3.2 脚手架当前的实现（兜底，仅供跑通流程）

如果你只是要快速跑通流程，脚手架的默认实现是：

| 环节 | 存到哪 | 说明 |
|---|---|---|
| 部署流程时 | `wf_deploy_form.content` | **表单快照**，保证流程实例用的表单版本稳定 |
| 发起/审批提交时 | `wf_task_form.form_content` | 把整个表单 JSON 文本按「流程实例 + 节点」存一份（脚手架的兜底做法，**生产应改 6.3.1 的方案**） |

**表单定义(`wf_form.content`)改了,快照不会自动更新**——必须重新部署流程。这是最容易踩的坑,见[第十二章](#十二常见问题排查)。

### 6.4 表单模板（素材库）

`表单管理` 页内的「表单模板」功能（`wf_form_template`）只是**JSON 文本容器**：

- 把设计好的表单 JSON 从「表单管理」复制过来粘贴保存；
- 列表可「预览」（用与审批一致的表单渲染器渲染）；
- 用途是团队内复用表单布局，**不会自动参与流程**。

## 八、审批操作详解

### 8.1 在哪里审批

| 入口 | 能做什么 |
|---|---|
| `我的待办` 列表 | 每行直接点审批按钮（按钮由**该行节点**的授权功能动态生成） |
| `流程详情` 页（带 `taskId` 进入） | 左侧看流程图/流程表单，右侧看当前任务 + 审批按钮 + 审批记录 |
| `待签收` 列表 | 候选任务先「签收」，再回待办办理 |

> 详情页只有**带 `taskId`** 进入时才显示审批按钮；看已结束的流程没有当前任务，也没有按钮，属正常。

### 8.2 各操作的区别（重点）

| 操作 | 流程会怎样 | 历史记录 | 典型场景 |
|---|---|---|---|
| **同意** | 流转到下一节点，可同时填审批意见、流程变量、业务表单、抄送人 | 保留 | 正常通过 |
| **驳回** | **直接结束整个流程**，状态标为「已驳回」，发起人要重新发起 | 保留 | 一票否决 |
| **退回** | 退回到**指定节点**，流程继续流转（不是结束） | 保留 | 打回上一环节补材料 |
| **转办** | 任务转给他人，**处理完不再回到自己** | 保留 | 我不方便办，交给别人 |
| **委派** | 委派他人处理，**处理完回到自己确认** | 保留 | 我拿不准，请人先看 |
| **前加签** | 在当前节点**前**插入审批人（可多选）。被加签人先办，办完**回到操作人**，操作人再办一次才流转 | 保留 | 临时加一位领导先看 |
| **后加签** | 在当前节点**后**插入审批人（可多选）。操作人先办完（被引擎自动 complete 自己的子任务），再让被加签人补审，办完才流转 | 保留 | 办完再让某人过目 |
| **会签回退** | **仅顺序会签节点**：退到本节点上一位已处理的审核人重办 | 保留 | 会签顺序中发现问题 |
| **终止** | 结束整个流程 | 保留 | 流程作废但记录在案 |
| **撤回** | 发起人把流程撤回来（`我的已发`） | 保留 | 发错了 |
| **跳过节点** | 由权限 `workflow:process:skipUserTask` 控制，跳过当前/指定节点 | 保留 | 特殊处理 |
| **变更处理人** | 直接改任务处理人（`editProcessTaskAssignee`） | 保留 | 原处理人离职/休假 |
| **废除** | 终止 + **物理删除**（历史、审批意见、扩展信息、抄送、表单数据全删） | **不保留** | 测试数据清理 |

> **前加签 vs 后加签的直观对比**（小李在 A 节点被加签给张三）：
>
> | 时刻 | 前加签 | 后加签 |
> |---|---|---|
> | 操作人点按钮后 | 小李的 A 任务**挂起**（assignee 清空） | 小李的 A 任务**被引擎自动 complete** |
> | 谁先看到待办 | 张三 | 张三（小李那一份已没） |
> | 张三办完后 | 小李的 A 任务**回来**，小李再办一次才流转 | 直接流转到下一节点 |
> | 适用 | 让专家先过一遍，自己再拍板 | 自己先表态，再让人把关 |

### 8.3 审批弹窗里有什么

| 区域 | 内容 | 说明 |
|---|---|---|
| 审批意见 / 原因 | 同意 / 驳回 / 退回 / 会签回退 / 终止 时出现，**必填** | 写进 `act_hi_comment` + `wf_comment_info`。label 随 action 变化（"审批意见"/"驳回原因"/"退回原因"/"回退说明"/"终止原因"） |
| 加签留言 | 前加签 / 后加签 时出现，**选填** | 写给被加签人的说明。空串也允许提交 |
| 接收人 / 加签人 | 转办、委派（单选）；前加签 / 后加签（多选） | — |
| 退回节点 | 仅「退回」，下拉列出**可退回节点** | 后端只列"已办过且能到达当前节点"的节点 |
| 流程变量 | 同意 / 驳回时可填 **JSON** | 格式错误会直接提示，要求改成合法 JSON |
| 业务表单 | 节点绑定的表单，填写的值随任务提交保存 | 脚手架默认存在 `wf_task_form.form_content`（**生产应改：业务字段值落业务表**，见 §6.3.1） |

> 弹窗顺序上「审批意见」在上、业务表单在下，是为了避免把意见填进业务表单字段里。

### 8.4 抄送怎么发

节点授权功能里勾了 `copy` 后，节点就"允许抄送"。抄送是**随同意/驳回等动作一起提交**的（没有独立的抄送按钮）：

- 抄送对象去「**抄送我的**」能看到该流程；
- 可以点「抄送已读」标记已读（`readCopy`）。

### 8.5 流程图上的颜色

流程详情页的流程图用 bpmn-js 渲染，并按状态着色：

| 颜色 | 含义 |
|---|---|
| 🟠 橙色 | 当前待处理节点（重点） |
| 🟢 绿色 | 已办节点 / 已走过的连线 |
| 🔴 红色 | 驳回节点 |

## 九、流程中心：终止与废除的区别

`流程中心`（`/workflow/center`）有三个页签：

| 页签 | 内容 |
|---|---|
| 未完结 | 引擎级"未完成"的实例（`running`） |
| 已完结 | 引擎级"已完成"的实例（`completed`） |
| 已终止 | 已完结但流程状态变量为 `canceled` 的实例 |

列表支持按流程名称 / 流程标识 / 发起人 ID 查询，操作有「详情」「终止」「废除」，并支持批量。

| 操作 | 数据影响 | 可恢复 |
|---|---|---|
| **终止** | 只结束流程；历史、审批意见、表单快照、抄送**全部保留**，业务侧仍能查到"已终止" | — |
| **废除** | 先终止，再**物理删除** Flowable 历史 + `wf_comment_info` + `tbl_flow_extend_procinst` + `wf_copy` + `wf_task_form` | ❌ 不可恢复 |
| **清空全部流程数据** | 比废除更彻底：连流程定义、部署、模型、分类、表单一起清掉（详见 [§4.8](#48-流程数据清盘一键清空危险操作)） | ❌ 不可恢复 |

> 界面上的确认弹窗已经写明这一点。**生产环境慎用废除**。
>
> 三种操作的破坏力递增：**终止 < 废除 < 清空全部流程数据**。前两个作用于选中的流程实例，第三个是全局清盘。

流程状态变量的取值与界面文案：

| 值 | 界面文案 |
|---|---|
| `running` | 进行中 / 流转中 |
| `completed` | 已完结 / 已结束 |
| `stop` | 已终止 |
| `cancel` | 已撤销 |

| **流程替换**（迁移到新流程定义） | `workflow:process:migrate` | — |
| **清空全部流程数据** | `workflow:process:clearAll` | — |

> 授权给角色：`系统管理 → 角色管理 → 修改 → 菜单权限` 勾选对应项即可（权限项已在 SQL 脚本里初始化好）。
>
> **历史变更**：之前版本「终止 / 前加签 / 后加签」只需要菜单权限、不需要节点授权功能。当前版本已并入授权功能，节点不勾选则按钮不出现（即便用户有菜单权限）。这意味着：
>
> 1. **新建节点**：在设计器里按需勾选即可；
> 2. **存量模型**：升级后需要重新打开模型，勾选需要的新项后**重新部署**才会生效；存量在跑的实例仍按旧规则走；

## 十二、常见问题排查

### Q1：待办里点不到审批按钮 / 提示"当前节点未配置授权功能"

按顺序检查：

1. **节点授权功能**是否勾选（设计器 → 点该用户任务 → 授权功能）；
2. 勾了之后**是否重新保存并部署**（不重新部署，运行中的流程实例仍用旧定义）；
3. 当前登录用户的**角色是否有对应菜单权限**（第十章表格）；
4. 若只有「终止」没有其他按钮，说明授权功能整体为空。

### Q2：表单改了，审批时看到的还是旧的

这是**设计如此**：流程审批读取的是 `wf_deploy_form.content`（部署时的快照）。
解决：`流程模型 → 设计 → 保存流程`（自动重新部署），新发起的实例才会用新表单；已在跑的实例保持旧快照。

### Q3：模型列表里没有"发起"入口 / 测试启动页提示"暂无可启动的流程"

- 模型是否**已部署**？（状态=已部署）
- 是否被**挂起**？（已挂起不能发起新的）
- 模型是否至少有一个**开始事件**且流程合法？

### Q4：发起时报流程变量 JSON 错误

「流程变量」必须是**合法 JSON 对象**，例如 `{"days":5}`；`{days:5}` 缺引号会被拒。

### Q5：审批提交报"请先完善表单中的必填项"

节点绑定的业务表单里有必填字段没填。审批弹窗里的**业务表单**与上面的**审批意见**是两套独立数据，都要按要求填。

### Q6：审批同意了，但下一节点没人收到任务

- 下一节点的**审批人配置为空**：可开启「为空跳过」或修正人员/表达式；
- 审批人用的是**候选人员**：任务进了「待签收」，需要候选人先签收；
- 用的是**表达式**：确认表达式引用的流程变量确实存在（发起时的"流程变量"）。

### Q7：能不能直接改数据库把流程挪到下一步？

**不要**。`act_ru_*` / `act_hi_*` 之间有一致性约束，手工改会导致流程图、审批意见、待办三者对不上。
正确做法：用界面提供的**退回 / 变更处理人 / 跳过节点 / 终止**，或走管理接口。

### Q8：改了流程定义，正在跑的实例怎么办？

已经启动的实例**继续按原版本**走完，这是 Flowable 的标准行为，对生产是好事。
如果必须让某个实例用新定义，只能终止后重新发起（或用「变更处理人/跳过」把当前实例推完）。

### Q9：流程图打不开 / 显示"暂无流程图"

- 该模型**未部署**时无法预览流程图；
- 流程实例可能没有对应的 PNG/XML 资源（历史数据被清理）；
- 详情页右上角若报错，看后端日志中 `ProcessViewer` 相关异常。

### Q10：会签回退按钮不出现

两个条件缺一不可：节点是**顺序会签**（多实例+顺序审批开启）**且**授权功能里勾了「会签回退」。

### Q11：前加签 / 后加签 / 终止按钮不出现

这三个动作在旧版是按菜单权限直接显示，**当前版本已并入节点「授权功能」**：

1. 打开流程设计器，点对应用户任务节点；
2. 在右侧面板「**授权功能**」里**勾选**「前加签」「后加签」或「终止」；
3. **保存并部署**（只有新部署的模型生效，已经在跑的实例仍按旧定义走）；
4. 还需要当前用户有对应菜单权限（`workflow:process:beforeAddSignTask` / `afterAddSignTask` / `workflow:process:cancel`），见[第十章](#十权限对照表)。

> 升级前的存量模型**不会自动多出这三个按钮**——必须重新打开、勾选、重新部署。

### Q12：后加签之后小李的待办没了，张三办完直接到下一节点

这是**预期行为**，不是 bug。后加签的语义是"**小李先表态，张三再补审**"：

| 时刻 | 小李 | 张三 |
|---|---|---|
| 后加签提交 | 当前 A 任务被引擎自动 complete | A 任务出现在张三的待办 |
| 张三办完 | 无操作 | — |
| 流程流向 | A 节点结束，**直接流转到下一节点**（不回到小李） | — |

如果想要"张三办完再回到小李"，用**前加签**（见 §8.2 对比小表）。
