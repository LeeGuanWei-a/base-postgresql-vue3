# 流程引擎使用说明

> 适用项目：`base-postgresql-vue3`（分支 `springboot4-extend-flowable`）
> 后端：**Spring Boot 4.1.1 + JDK 21**；前端：Vue 3.5 + Element Plus 2.13 + bpmn-js 17.11 + vform3
> 引擎：**Flowable 8.0.0**（`flowable-spring-boot-starter-process`）+ 本项目自研的流程定制层 `extend-flowable/`
> 数据库：PostgreSQL，schema **`basicdb_flowable8`**（92 张表：`act_*` 引擎表 + `flw_*` 事件/批处理表 + `wf_*` 业务表 + `tbl_flow_extend_procinst`）
> 本文面向**使用者**：怎么画流程、怎么发起、怎么审批、怎么退回/转办/委派/前加签/后加签/会签回退/终止/撤回/废除/抄送、怎么结束。
> 集成原理、模块结构与版本差异见 [README 第十二章](../README.md#十二flowable-流程引擎集成)。

## 一、开始之前

### 1.1 前置条件

| 项 | 要求 |
|---|---|
| 数据库 | PostgreSQL ≥ 15，已导入 `file-sql/basicdb-vue3.sql`（含全部 `act_*` / `flw_*` / `wf_*` 表与菜单权限数据） |
| 后端 | `basic-admin-api` 启动成功，端口默认 `8080`（模块 `extend-flowable` 已列入父 pom 的 `<modules>`） |
| 前端 | `web-ui` 已 `pnpm install` 并 `pnpm dev` |
| 账号 | `admin` / `admin123`（超级管理员，建议登录后立即改密） |

### 1.2 关键配置

流程引擎相关配置在 [basic-admin-api/src/main/resources/application.yml](../basic-admin-api/src/main/resources/application.yml)：

```yaml
spring:
  flowable:
    database-schema-update: true          # 启动时检查/增量同步引擎表结构
    history-level: audit                  # 历史级别：实例 + 变量 + 表单属性
    check-process-definitions: false      # 不自动部署 resources/processes 下的 BPMN（本项目没有该目录）
    database-schema: basicdb_flowable8    # 锁定引擎表所在 schema，必须与 JDBC URL 的 currentSchema 一致
    idm:
      enabled: false                      # 关闭 Flowable 自带 IDM，用户/角色走 sys_user / sys_role
    form-field-validation-enabled: false  # 关闭 Form Service 字段强校验，表单走自定义 JSON
```

几个容易踩的点：

| 注意点 | 说明 |
|---|---|
| `flowable.idm.enabled` | 这是 Flowable 7/8 的正确键。历史写法 `flowable.common.app.idm-enabled` **是无效键**，会被静默忽略，结果仍会建出 `ACT_ID_*` 表（不影响运行，可保留或手工删） |
| `database-schema` | 必须和 JDBC URL 的 `currentSchema=basicdb_flowable8` 一致，否则引擎建表/查表会落到别的 schema |
| 配置键写错不报错 | Flowable 的配置键以 `flowable-spring-boot-autoconfigure` 的 `spring-configuration-metadata.json` 为准，写错的键会被**静默忽略**，排查时以日志与表结构为准 |
| `allow-circular-references` | `spring.main.allow-circular-references: true` 是打开着的：`extend-flowable` 里大量 `Wf*Service` 相互持有（A 字段里有 B、B 字段里有 A），Spring Boot 3+ 默认禁止循环引用会直接启动失败 |
| 引擎表不会自动补齐业务表 | `database-schema-update: true` 只保证 `act_*` / `flw_*` 引擎表存在；`wf_*`、`tbl_flow_extend_procinst`、`flw_expression` 这些**业务表来自 SQL 脚本** |

### 1.3 与 `master-extend-flowable`（Flowable 6.8）的差异

| 维度 | `master-extend-flowable` | 本分支（`springboot4-extend-flowable`） |
|---|---|---|
| 引擎版本 | Flowable **6.8.0** | Flowable **8.0.0** |
| 平台 | Spring Boot 2.5.14 + JDK 11 | Spring Boot **4.1.1** + JDK **21** |
| 数据库 schema | `basicdb_flowable`（86 张表 + 2 视图） | **`basicdb_flowable8`**（92 张表） |
| 模型存储 | 模型编辑器源是设计器 **JSON** | Flowable 7 起移除了 `flowable-json-converter`，模型编辑器源改为 **BPMN XML**（`WfModelSaveXmlService` 写入、`WfModelQueryXmlService` 读取） |
| 建模器表 | 存在 `act_de_*`（flowable-ui-modeler） | **没有 `act_de_*`**（本项目不装 modeler UI），模型只落 `act_re_model` + `act_ge_bytearray` |
| 前端页面目录 | `web-ui/src/views/workflow/**` | 按业务域重组为 **`web-ui/src/views/basic-extend/workflow/**`** |
| 前端依赖 | bpmn-js 较低版本 | **bpmn-js 17.11.1** + `bpmn-js-properties-panel 5.28` + `@bpmn-io/properties-panel 3.57` + **vform3-builds 3.0.10** |
| 菜单区段 | `sys_menu` 1500 起 | 同样是 **1500～1699**（1 个目录 + 11 个页面 + 117 个按钮权限） |
| 权限串 | 部分差异 | 见[第十章](#十权限对照表)（本分支实际 `@PreAuthorize` 值） |

> 功能层面两者一致：建模 → 部署 → 发起 → 审批（同意/驳回/退回/转办/委派/加签/会签回退/终止）→ 抄送 → 撤回 → 废除，外加**边界事件**、**流程替换（迁移）**、**流程数据清盘**三块增强能力。

### 1.4 两个必须知道的概念

| 概念 | 含义 | 存在哪 |
|---|---|---|
| **流程模型（Model）** | 设计器里画的那张流程图，可以反复改、有历史版本 | `act_re_model` + BPMN XML 落在 `act_ge_bytearray` |
| **流程定义（ProcessDefinition）** | 模型**部署**后的产物，是真正能被发起的东西 | `act_re_procdef` + 部署资源 |

**一次部署 = 一个版本**。改了模型并重新部署，版本号 +1；已经在跑的流程实例仍按旧版本走完，不受影响。

> 本分支的模型**没有 `act_de_*` 表**：设计器保存时把 BPMN XML 写回模型编辑器源（`act_ge_bytearray`），列表页与设计页都从那里读。

## 三、从零跑通一条流程（四步）

下面用一个「请假审批」的例子串起完整链路，**建议第一次就按这个顺序走**。

### 第 1 步：建流程分类

`流程引擎 → 流程分类 → 新增`

| 字段 | 说明 | 示例 |
|---|---|---|
| 上级分类 | 支持树形；顶级留空 / 选 0 | 顶级 |
| 分类名称 | 显示名 | 人事流程 |
| 分类编码 | **英文唯一标识**，模型靠它归属分类 | `hr` |

> 分类编码（`code`）是模型与分类之间的关联键，不是分类 ID。建模型时选的就是这个编码。
> 新增/修改前会校验编码唯一（`checkCategoryCodeUnique`，更新时排除自身）；删除时若存在**下级分类**会被拒绝，避免孤儿分类。

### 第 2 步：建流程模型

`流程引擎 → 流程模型 → 新增`

| 字段 | 说明 |
|---|---|
| 模型名称 | 显示名，如「请假审批」 |
| 模型标识 | **英文唯一标识**，如 `leave`。发布流程时后端会拼成 `leave.bpmn` 去匹配流程定义 |
| 流程分类 | 选第 1 步建的分类 |
| 备注 | 选填 |

点「确定」后**自动进入流程设计器**。

### 第 3 步：画流程图并保存

拖节点、连线、配审批人（见[第四章](#四流程设计器详解)、[第五章](#五节点配置审批人与授权功能)），点「**保存流程**」。系统依次做三件事：

1. `saveModel`：把 **BPMN XML** 写回模型（`WfModelSaveXmlService`）；
2. 保存前做**流程合规校验**（`WfProcessComplianceValidator`）：开始/结束节点、用户任务处理人、边界事件等，问题一次性列出；不通过则弹窗显示问题清单，不会保存；
3. 保存成功后**立即自动部署**（`deployModel`），提示「保存并部署成功」并返回模型列表。

> 如果出现「保存成功，但自动部署失败」，模型仍是已保存状态，可以回列表手动部署。

保存并部署后，列表里该模型的状态：

| 状态 | 含义 | 可执行操作 |
|---|---|---|
| 未部署 | 只存了模型，还不能发起 | 设计、删除 |
| 已部署 | 可以发起新流程 | 设计、停用、删除 |
| 已挂起 | 不能发起新的，**已发起的流程不受影响** | 设计、激活、删除 |

### 第 4 步：发起并审批

- **发起**：流程模型列表里对已部署的模型点「发起」，或走「测试启动流程」页；发起成功拿到 `procInsId`，业务系统应保存它作为与流程的关联依据。
- **审批**：切到被指派的账号，进「我的待办」，点行内审批按钮或「详情」。

## 四、流程设计器详解

设计器基于 **bpmn-js 17.11**，页面 `/workflow/model/design`（`model/design.vue`），挂载两个自定义插件：

- 自定义 Palette（左侧元素面板）
- 自定义 ContextPad（选中元素后的快捷菜单，「Append task」创建的是 **UserTask** 而不是抽象 Task）

### 4.1 画布基本操作

| 操作 | 方式 |
|---|---|
| 添加节点 | 从左侧面板拖到画布 |
| 连线 | 选中节点 → 拖动节点边缘箭头到目标节点 |
| 修改属性 | 点击节点，右侧属性面板出现对应页签 |
| 删除 | 选中后按 Delete，或右键 |
| 缩放 / 平移 | 鼠标滚轮 / 按住空白处拖动 |

### 4.2 节点与连线类型

| 元素 | 用途 |
|---|---|
| 开始事件（StartEvent） | 流程唯一入口，**必须配置表单**（发起人在这里填单） |
| 用户任务（UserTask） | 需要人审批的节点，使用频率最高 |
| 排他网关（ExclusiveGateway） | 按条件走**其中一条**分支（如金额 > 5000 走总经理） |
| 并行网关（ParallelGateway） | 分支同时进行，全部到达后继续 |
| 包含网关 / 事件网关 | 更复杂的汇聚 / 事件驱动场景 |
| 服务任务 | 系统自动执行（需自行配置委托表达式） |
| 子流程 / 调用活动 | 流程内嵌或调用另一条流程 |
| 边界事件 | 挂在用户任务/子流程/调用活动**边界**上，做「异步分流」；支持 8 种类型，见 [§4.6](#46-边界事件boundary-event-详解) |
| 结束事件 | 流程终点 |

### 4.3 连线条件（网关分支）

选中**从网关出发的连线**，右侧出现「条件」页签：

| 类型 | 写法 | 例子 |
|---|---|---|
| 表达式（expression） | `${...}` | `${days > 3}` |
| 内联脚本（inlineScript） | 选脚本语言后写脚本 | — |
| 外部脚本（externalScript） | 写资源地址 | — |

还可以设**默认流（default flow）**：所有条件都不命中时走这条。

> 表达式里能引用的变量 = 发起时填的「流程变量」+ 审批过程中写入的变量。
> 例如发起时传 `{"days":5}`，则 `${days > 3}` 命中。

### 4.4 其他可用配置

| 配置项 | 位置 | 说明 |
|---|---|---|
| 表单标识 | 元素属性 → 表单 | 给节点绑定业务表单（见第六章） |
| 执行监听器 / 任务监听器 | 元素属性 → 监听器 | 支持类、表达式、委托表达式、脚本 |
| 多实例 | 元素属性 → 多实例 | 会签 / 或签、集合、元素变量、完成条件 |
| 流程变量 localScope | 元素属性 | 控制变量作用域 |

### 4.5 常用扩展属性（节点上落库的样子）

设计器把面板上的开关写成 BPMN 扩展属性（前缀 `flowable:`），运行时由引擎缓存的 `BpmnModel` 直接读，**不产生额外库查询**。
属性名以 `extend-flowable` 的 [ExtensionConstant](../extend-flowable/src/main/java/com/basic/constant/ExtensionConstant.java) 为准：

| 扩展属性 | 对应面板项 | 值 |
|---|---|---|
| `assigneeType` | 审批人来源 | `0` 固定值 / `1` 身份存储 |
| `idmPermission` | 授权功能 | JSON 数组文本，如 `["complete","reject","return"]` |
| `idmCandidateUsers` | 候选人员 / 分配人员 | JSON 数组文本（用户 id） |
| `idmCandidateGroups` | 候选角色 | JSON 数组文本（角色 id） |
| `idmAssignee` | 分配人员（单人） | 单人 id 文本 |
| `isSkip` | 处理人配置 → 自动跳过 | `true` / `false` |
| `isNullSkip` | 为空跳过 | `true` / `false` |
| `isExamined` | 审批配置（同一处理人只需审批一次） | `true` / `false` |
| `isRoleReplace` | 交替配置（连续节点处理人相同则跳过） | `true` / `false` |
| `isRevoke` | 强制撤回多实例节点存在已审的情况 | `true` / `false` |
| `isUserScreen` / `isOrgScreen` / `isDeptOrOrg` | 人员筛选 / 组织筛选 / 部门或组织 | `true` / `false` |
| `nodeType` | 节点类型标记 | 见设计器面板 |
| `isEditData` | 是否允许编辑数据 | `true` / `false` |

> 写节点扩展时**不要写空数组**：例如空的 `idmCandidateUsers` 会在重新打开节点时把「分配」方式抢成另一种，表现成「明明选了角色，打开却变了」。

### 4.6 边界事件（Boundary Event）详解

边界事件是挂在某个活动（UserTask / SubProcess / CallActivity）**边界**上的钩子。当该活动正在执行、且条件命中（时间到 / 收到消息 / 收到信号 / 抛错…），流程就从**这个钩子的出向连线**流走——和正常审批出向**同时存在**。

区别：**主出向是「审完才走」**，边界事件是「**还没审完就被另一件事打断**」。

#### 4.6.1 8 种类型

设计器 palette 里 8 种都画成同一个「中间/边界事件」图标，具体类型要选中后**在右侧「边界事件」分组的下拉框里选**（拖出后默认「未指定」）。

| 类型 | 何时触发 | 触发后 | 典型场景 | 能否挂 UserTask |
|---|---|---|---|---|
| **定时器（timer）** | 时间到（duration / cycle / date） | 沿出向连线流走 | 审批 24 小时没审，自动走超时分支 | ✅ |
| **消息（message）** | 外部调 `messageEventReceived(name, execId)` | 同上 | 等另一个流程发来的「审核完成」消息 | ✅ |
| **信号（signal）** | 外部调 `signalEventReceived(name)` | 同上 | 全局广播（某产品下线，所有挂该 signal 的流程同时响应） | ✅ |
| **错误（error）** | ServiceTask / JavaDelegate 抛 `BpmnError(code)` | 同上 | 调外部接口超时 / 业务校验失败，进「出错分支」 | ✅ |
| **升级（escalation）** | 节点抛 `BpmnEscalation(code)` | 同上 | 轻度异常，语义比 error 轻 | ✅ |
| **取消（cancel）** | 事务 / 外部取消 | 同上 | 发起人撤销 → 子流程进入「撤销后处理」 | ⚠️ 仅 transaction / call activity 子流程边界有效，挂 UserTask 不触发 |
| **补偿（compensation）** | 外部 throw compensation | 同上 | 流程回滚，撤销前面已办的事 | ✅（需与 throw compensation 配合） |
| **条件（conditional）** | 条件表达式为 true | 同上 | `${amount > 10000}` 超阈值直接升级 | ✅ |

#### 4.6.2 画一个边界事件

1. 从左侧 palette 拖出**中间/边界事件**图标；
2. 放到**目标活动的边框上**（放中间就变成中间事件了，行为完全不同）；
3. 选中后右侧「边界事件」分组里选「**事件类型**」；
4. 选完类型，对应配置面板（时长 / 错误码 / 信号 code 等）出现在下方，填必填项；
5. 画一条**出向连线**连到目标节点；
6. 点「保存流程」——保存前会校验，没填的必填项列在弹窗里。

> **取消活动（cancelActivity）**：勾上（默认）触发时**中断**宿主活动；去掉则**不中断**，boundary 走另一条并行分支。
> 例如「24 小时没审就催办」通常**不勾**——催办和正常审批并存。

#### 4.6.3 中断 vs 非中断

bpmn-js 在调色板里把两种画成两个独立图标。**本项目当前仅支持「中断」型**；非中断边界事件未在转换器里注册，需要时再补。

#### 4.6.4 后端触发接口

把「信号 / 消息 / 错误 / 取消」4 种外部可触发类型封装成接口，业务系统不写 Java 代码也能驱动流程（`WfBoundaryEventController`，基路径 `/workflow/boundary`）：

| 接口 | 路径 | 权限 |
|---|---|---|
| 触发信号 | `POST /workflow/boundary/signal` | `workflow:boundary:trigger` |
| 触发消息 | `POST /workflow/boundary/message` | `workflow:boundary:trigger` |
| 触发错误（写标志变量） | `POST /workflow/boundary/error` | `workflow:boundary:trigger` |
| 触发取消 | `POST /workflow/boundary/cancel` | `workflow:boundary:trigger` |
| 查询实例的 boundary 列表 | `GET /workflow/boundary/list/{procInsId}` | `workflow:boundary:query` |

请求体统一为 `WfBoundaryTriggerBo`：

```json
{
  "procInsId": "a1b2c3d4-...",
  "eventCode": "approval-passed",
  "comment": "由业务系统在订单完成后回调",
  "variables": { "amount": 8500 }
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `procInsId` | ✅ | 流程实例 id（发起接口返回） |
| `eventCode` | signal / message / error 必填 | 信号名 / 消息 id / 错误码，对应 boundary 上配的 `signalCode` / `messageId` / `errorCode` |
| `comment` | ❌ | 触发原因，写入流程变量 `boundaryTriggerComment` |
| `variables` | ❌ | 附加流程变量 |

> **错误边界没有「从外部直接抛 BpmnError」的标准接口**（`RuntimeService` 不支持）。`triggerError` 的实现是往流程变量里写错误码标志，由业务侧 ServiceTask / JavaDelegate 监听后调 `execution.bpmnError(code)` 抛出。
> **定时器与条件不需要外部触发**：引擎自己到点 / 表达式自己求值。

#### 4.6.5 流程变量约定

触发成功后，流程变量 `processStatus` 会被改写成 `boundary_<type>`（如 `boundary_signal` / `boundary_error`），便于按「被 boundary 触发的流程」筛选。

流程正常结束后，`GlobalEventListener` 监听 `PROCESS_COMPLETED` 把状态归一化：

| 触发前 | 触发后 |
|---|---|
| `running` | `completed` |
| `boundary_<type>` | `completed` |
| `canceled` | 保持 `canceled` |

#### 4.6.6 保存前的合规校验

`WfProcessComplianceValidator`（`service/wfModel/validate/`）在保存流程时一并校验 boundary，不通过会在设计器弹窗列出：

| 规则 | 大致提示 |
|---|---|
| boundary 必须挂在活动上（`attachedToRef`） | 边界事件[...] 没有挂在任何活动上 |
| boundary 必须有事件定义 | 边界事件[...] 没有配置事件定义 |
| timer 必须配 duration / cycle / date | 定时器边界事件[...] 没有配置时长 |
| error 必须配 errorCode | 错误边界事件[...] 必须配置 errorCode |
| cancel 不能挂 UserTask | 取消边界事件[...] 仅在 transaction / call activity 子流程边界有效 |
| 同一宿主同类型 boundary 重复 | 宿主活动[...] 上挂了 N 个同类型边界事件 |

> 这些是**业务侧经验规则**，不是 BPMN 规范硬要求。例如「同宿主同类型重复」Flowable 不拦，但运行期行为未定义，所以校验器提示合并。

#### 4.6.7 与「超时不审批」的关系

`ProcessDueTimeListener` 目前只是**骨架**（读到活动与实例信息后打日志），没有接业务动作。

> **推荐做法**：用 **timer 边界事件**替代——在需要超时的 UserTask 边框上挂 timer，配 `PT24H`，出向连到「超时处理」节点（自动通过 / 转上级 / 结束）。
> 引擎自带的 Job Executor 会到点触发，不需要额外监听器。

### 4.7 流程替换（运行中实例迁移到新流程定义）

#### 4.7.1 这是什么

人事变动 / 业务模式变更后，**已发起的流程**需要换走新流程定义，例如：

- 旧流程某 UserTask 的审批人 A 离职，新版本换成 B
- 旧流程某 UserTask 被删了，新流程调整了分支
- 业务部门重写流程图，要求历史在途流程按新版本继续走

「流程替换」把一条**正在跑**的实例**整条迁到新流程定义**继续跑：沿用旧流程启动人 / 业务名，复制历史意见与附件，可选地镜像推进若干节点，最后废除旧流程。

#### 4.7.2 提供的接口

前端页面 `/workflow/migrate`（入口：**我的已发 → 行操作「流程迁移」**，会把旧 `procInsId` 带进去），后端 `WfProcessMigrateController`，基路径 `/workflow/process/migrate`：

| 接口 | 路径 | 权限 | 用途 |
|---|---|---|---|
| 触发替换 | `POST /workflow/process/migrate/replace` | `workflow:process:migrate` | 事务内执行，失败整体回滚 |
| 校验参数 | `POST /workflow/process/migrate/validate` | 同上 | 不实际执行 |
| 列出新流程的用户任务 | `GET /workflow/process/migrate/userTasks/{processDefinitionKey}` | 同上 | 页面用来展示"可推进节点"与旧流程走过/没走过 |
| 旧流程当前任务 | `GET /workflow/process/migrate/currentTask/{procInsId}` | 同上 | 页面顶部回显 |
| 调试用定义详情 | `GET /workflow/process/migrate/debug/definition/{processDefinitionKey}` | 同上 | 排查用 |

Service：`IWfProcessMigrateService.replaceProcessInstance(plan)`，失败抛 `WfProcessMigrateException`。

#### 4.7.3 替换计划 WfProcessMigratePlan

```java
// 推荐写法：不传 advanceSteps，自动按旧流程历史镜像
WfProcessMigratePlan plan = WfProcessMigratePlan.builder()
    .oldProcInsId("a1b2c3...")                  // 必填：旧流程实例 id
    .newProcessDefinitionKey("payOld")          // 必填：新流程定义 key（不带 .bpmn，服务内部会补）
    .startVariables(Map.of("st", 0))            // 选填：启动新流程时附加的变量
    .copyComments(true)                         // 选填：复制历史意见，默认 true
    .copyAttachments(true)                      // 选填：复制附件，默认 true
    .reason("人事变动：A 离职，由 B 接替")        // 选填：会作为一条新意见写入新流程
    .businessCallback((oldId, newId) -> {        // 选填：业务表更新回调（旧 → 新）
        // 业务侧更新自己业务表里的 procInsId 字段
        // 不要在回调里发消息、调外部接口、起新流程
    })
    .build();
String newProcInsId = wfProcessMigrateService.replaceProcessInstance(plan).getNewProcInsId();
```

#### 4.7.4 镜像推进的两种模式

**模式 A：自动镜像（推荐，不传 `advanceSteps`）**

读旧流程的**已完成 userTask 历史**（`act_hi_actinst` 里 `activityType='userTask'` 且已结束，按结束时间升序），按同样顺序在新流程上逐个 `complete`：

- 旧流程走过哪些节点，新流程就走哪些节点
- 会签节点按旧流程**实际完成的次数**推进
- 旧流程因条件分支没走到的节点，不会被推
- 处理人沿用旧流程该节点的实际 `assignee`

**模式 B：手动指定 `advanceSteps`**

适用于「希望新流程比旧流程走得更远 / 更近」：

- 后端按**新流程图的真实走向顺序**（用 `sequenceFlow` 从 startEvent 做 BFS 算出）重排，**不是按传入顺序**
- 原因：bpmn 文件里元素声明顺序是画图顺序，不等于走向顺序；按声明顺序推会因「还没走到那里」查不到 task 被静默跳过
- 会签节点会自动循环推进，直到该 `taskDefinitionKey` 没有活动 task

> ⚠️ 手动模式下只勾**旧流程已经走过**的节点。勾上「旧流程当前停留的节点」会把新流程推**过**该节点（过冲）。迁移页用「已走过 / 未走过」标签标出每个节点状态。

#### 4.7.5 内部执行步骤

整个替换在**单一事务**内执行，**任何一步失败整体回滚**：

1. 校验旧流程存在且未结束、有启动人
2. 校验新流程定义存在且未挂起（key 不带 `.bpmn` 时自动补后缀再查一次）
3. 启动新流程（沿用旧流程启动人 / processName / appSn）
4. 镜像推进（未传 `advanceSteps` 时自动镜像）
5. 复制历史意见（按 procInsId 重写，每条加 `[从旧流程 xxx 复制]` 前缀）
6. 复制附件（按 processInstanceId 重新插入）
7. 写一条「流程替换：xxx（旧流程 yyy 已废除）」意见到新流程
8. 执行 `businessCallback`，让调用方更新业务表
9. **废除旧流程**：`abolishProcess` 先终止再删除旧实例的历史记录（见 [§9](#九流程中心终止废除与清空)）

> 第 9 步调 `WfTaskServiceImpl.abolishProcess`，它**只读 `WfTaskBo.procInsIdList`**（不看 `procInsId`），必须把实例 id 放进 list 才会真正废除。

**推进时以系统身份调用**：推进新流程节点会走 `WfTaskServiceImpl.complete`，其中含 `WfTaskAuthService.checkOperateAuth`（校验「这个任务是不是你的」）。迁移是**代表他人推进**，因此内部通过 `WfTaskAuthService.callAsSystem(...)` 以系统身份调用、跳过该校验：

- 该标记是 `ThreadLocal`，**只能由服务端代码设置**，HTTP 请求体无法设置，不构成越权入口
- 写入历史的「办理人」按优先级解析：步骤指定处理人 → 任务当前 assignee → 任务第一位候选人 → 旧流程发起人（兜底）

#### 4.7.6 HTTP 请求体

```json
{
  "oldProcInsId": "a1b2c3...",
  "newProcessDefinitionKey": "payOld",
  "startVariables": { "st": 0 },
  "copyComments": true,
  "copyAttachments": true,
  "reason": "人事变动：A 离职，由 B 接替",
  "advanceSteps": []
}
```

> `advanceSteps` **留空或省略**即走自动镜像（推荐）。
> HTTP 入口**不暴露 businessCallback**——业务回调只能通过 Service API（注入 lambda）传入。

#### 4.7.7 不能做什么

- 不能跨 modelKey 映射变量 / 表单（旧流程变量不会自动迁到新流程）
- 不能「部分迁移」——要么全换，要么不换
- 不能迁移「草稿」「已结束」的流程
- 不在事务内做「发消息 / 调外部接口 / 起新流程」——这些放外层

#### 4.7.8 与边界事件的关系

两者正交，可以同时用：边界事件负责「运行中从某条支线流走」，流程替换负责「整条实例迁到新定义」。

### 4.8 流程数据清盘（一键清空，危险操作）

> ⚠️ **这是本系统唯一的「不可恢复」全局操作**，会把流程相关的全部数据物理删除。
> 用途仅限：开发 / 测试环境重置、交付前环境清理。**生产环境请勿使用。**

#### 4.8.1 入口与二次确认

`流程引擎 → 流程中心`，右上角红色按钮「**清空全部流程数据**」（权限 `workflow:process:clearAll`）。两步确认：

1. **先看清单**：调 `GET /workflow/process/clear/preview` 展示运行中实例数 / 历史实例数 / 部署数 / 模型数 + 主要业务表行数
2. **再手打短语**：必须手动输入约定短语（`IWfProcessClearService.CONFIRM_TEXT`）才允许提交

后端同样校验这个短语（`POST /workflow/process/clear/all`），所以直接调 API 也得带对文字。

#### 4.8.2 清除范围

分 6 步执行，**整体一个事务，全有或全无**：

| 步骤 | 做什么 | 为什么必须这么做 |
|---|---|---|
| 1 | 运行中实例：`runtimeService.deleteProcessInstance` **强制终止** | 必须走引擎 API——一并清理执行树、任务、变量、身份链接、定时器作业、事件订阅，并维护历史 |
| 2 | 历史实例：`bulkDeleteHistoricProcessInstances` **分批**删 | 单次调用有数量上限 |
| 3 | 部署：`deleteDeployment(id, true)` 级联删 | 必须走引擎 API——它会驱逐引擎内部的流程定义缓存 |
| 4 | 模型：`deleteModel(id)` | 同上 |
| 5 | **应用级定义缓存**：`customDeploymentCache.clear()` | 自研的 `CustomDeploymentCache` 没有注册进引擎（全项目无 `setProcessDefinitionCache` 调用），只是 `WfBpmnModelServiceImpl` 自用；引擎删部署不会连带清它，不清就会出现「删完还能从内存读到已删定义」 |
| 6 | 残留表 + 业务表：动态 `DELETE FROM`，先过滤存在性 | 前 5 步通常已清空引擎表，这步兜底回收孤儿行并清业务表 |

**清空的表（46 张）**：

| 分类 | 表 |
|---|---|
| Flowable 运行时（13） | `act_ru_entitylink` `act_ru_identitylink` `act_ru_variable` `act_ru_task` `act_ru_actinst` `act_ru_event_subscr` `act_ru_deadletter_job` `act_ru_external_job` `act_ru_history_job` `act_ru_suspended_job` `act_ru_timer_job` `act_ru_job` `act_ru_execution` |
| Flowable 历史（10） | `act_hi_detail` `act_hi_varinst` `act_hi_tsk_log` `act_hi_attachment` `act_hi_comment` `act_hi_entitylink` `act_hi_identitylink` `act_hi_actinst` `act_hi_taskinst` `act_hi_procinst` |
| 定义 / 部署 / 模型（6） | `act_procdef_info` `act_re_procdef` `act_re_model` `act_re_deployment` `act_ge_bytearray` `act_evt_log` |
| 事件注册 / 批处理（6） | `flw_ru_batch_part` `flw_ru_batch` `flw_event_resource` `flw_event_definition` `flw_event_deployment` `flw_channel_definition` |
| 业务流程表（11） | `wf_task_form` `wf_deploy_form` `wf_comment_info` `wf_copy` `wf_category_org_link` `wf_category` `wf_form` `wf_form_category` `wf_form_template` `tbl_flow_extend_procinst` `flw_expression` |

> 表清单按**外键依赖从子到父**排序，避免外键约束报错。

#### 4.8.3 明确**不会**删除的东西

| 保留项 | 原因 |
|---|---|
| `act_ge_property` | 引擎 schema 版本与自增 id 计数器，删了引擎起不来 |
| `flw_ev_databasechangelog` / `flw_ev_databasechangeloglock` | Liquibase 变更日志，删了破坏启动时 schema 校验 |
| `sys_menu` / `sys_role_menu` | 菜单与权限配置，不属于「流程数据」 |
| `ACT_ID_*`（若存在） | 本项目 `flowable.idm.enabled=false`，若有残留表不影响运行，也不在清理范围 |

#### 4.8.4 清完之后要做什么

分类、表单、模型、流程定义**全被清掉**，顺序不能乱：

1. `流程分类 → 新增`（没有分类建不了模型）
2. `流程模型 → 新增` → 设计器画图 → 保存（保存即部署）
3. `表单管理 → 新增`（流程要挂表单的话）
4. 之后才能正常发起

> `flw_expression`（表达式字典）也会被清空，依赖它的表达式需重建。

#### 4.8.5 为什么不能用 `WHERE 1=1` 绕过

项目在 `MybatisPlusConfig` 注册了 `BlockAttackInnerInterceptor`，会拦截「没有 WHERE 的 DELETE」（`Prohibition of full table deletion`）。清盘 Mapper 用官方忽略机制：

```java
@InterceptorIgnore(blockAttack = "true")   // 只作用于本方法
int deleteAllFromTable(@Param("tableName") String tableName);
```

**不要试图用 `DELETE FROM t WHERE 1=1` 绕过**——`BlockAttackInnerInterceptor.fullMatch()` 会专门判断 `EqualsTo` 且左右字面量相等，`1=1` 正好命中。

**表名安全**：表名不能用预编译参数，所以做了三重校验——硬编码白名单 → 正则 `^[a-z_][a-z0-9_]*$` → `information_schema` 查库内是否存在。用户输入碰不到表名。

#### 4.8.6 表清单为什么要先查存在性

不同环境里 Flowable 的辅助表不一定都建了（`flw_event_*`、`flw_ru_batch*` 等）。PostgreSQL 中**一条语句失败会让整个事务进入 aborted 状态**，后续语句全部报错，所以必须先筛出真实存在的表再删。日志会打印跳过的表：

```
[process-clear] 以下表在当前库中不存在，已跳过：[...]
```

没有这行说明 46 张表全部存在且都被清了。

## 五、节点配置：审批人与授权功能

点击一个**用户任务**节点，右侧面板从上到下：

### 5.1 顶部开关（人从哪来）

| 面板项 | 含义 | 建议 |
|---|---|---|
| 是否通过组织架构筛选 | 开启后绑定的人员 / 表达式按所选组织筛选 | 多组织场景开启 |
| 筛选方式（部门 / 组织架构） | 二选一 | 单公司用「部门」 |
| 根据发起人所在部门筛选 | 只筛选与发起人同公司 / 部门的人 | 按需 |
| 是否强制撤回多实例节点存在已审的情况 | 允许撤回「已有人审但没审完」的会签节点 | 按需 |
| 审批配置（是否） | 开启后同一处理人处理相同节点只需一次 | 避免重复审批时开 |
| 交替配置（是否） | 两个连续节点处理人相同则自动跳过 | 减少无意义审批 |
| 处理人配置（自动跳过） | 连续节点处理人相同自动跳过 | 同上 |
| 为空跳过 | 处理人为空时跳过该节点 | 表达式可能算出空值时开 |

### 5.2 审批人来源：两个页签

| 页签 | 适用场景 | 配置方式 |
|---|---|---|
| **固定值** | 流程适用多个公司，审批人用**表达式**动态求值 | 「分配人员」填表达式，如 `${starter}`、`${deptLeader}` |
| **身份存储** | 流程只给单个公司用，审批人**直接选人 / 选角色** | 三选一：候选人员 / 候选角色 / 分配给流程发起人 |

身份存储的「候选人员」会让任务进**待签收**，候选人之一先签收（claim）再办理。

> 固定值里的表达式可以写引擎表达式（`${...}`），也可以引用「表达式管理」里维护的字典项（`flw_expression`）。

### 5.3 授权功能（决定审批时有哪些按钮）

**最关键的一项**：勾了什么，审批人就看到什么按钮。

| 值 | 按钮文案 | 含义 |
|---|---|---|
| `complete` | 同意 | 通过并流转到下一节点 |
| `reject` | 驳回 | **直接结束流程**（状态标为「已驳回」），发起人需重新发起 |
| `return` | 退回 | 退回到**指定节点**，流程继续流转 |
| `transfer` | 转办 | 转给他人处理，**处理完不再回到自己** |
| `delegate` | 委派 | 委派他人处理，**处理完回到自己确认** |
| `copy` | 抄送 | 允许该节点在审批时抄送（**不是独立按钮**，随同意/驳回一起提交） |
| `mulitiSequentialUnComplete` | 会签回退 | **顺序会签专用**：回退到本节点上一位已处理的审核人 |
| `addSignBefore` | 前加签 | 在当前节点前插入审批人（可多选） |
| `addSignAfter` | 后加签 | 在当前节点后插入审批人（可多选） |
| `stop` | 终止 | 结束整个流程（历史、意见、表单保留） |

选项来源：

1. **字典** `wf_process_permission`（`sys_dict_data`，`dict_value` 即上表的值）——可在「系统管理 → 字典管理」维护；
2. **前端兜底** `web-ui/src/plugins/package/penal/task/task-components/UserTask.vue` 的 `permissionOptions`——字典没配置时用它，避免复选框空白。

> ⚠️ 当前库（`basicdb_flowable8`）里**没有 `wf_process_permission` 字典数据**，实际用的是前端兜底清单。
> 若要集中维护，可在字典管理里新增该字典；任何一处加新值，三个地方要同步：这里、设计器（字典/兜底）、前端 `actionMeta.js`。

**为什么我的审批按钮不见了？** 两个条件必须同时满足：

1. 节点「授权功能」勾了对应项（后端从 `idmPermission` 扩展读出，接口返回 `permissionJson`）；
2. 当前用户角色有对应菜单权限（见[第十章](#十权限对照表)）。

> 历史版本里「终止 / 前加签 / 后加签」不属于授权功能，**当前版本已并入**。存量模型需重新打开勾选后**重新部署**，新发起的流程才有这三个按钮。

### 5.4 多实例：会签 / 或签

节点选了候选人员或候选角色（或固定值表达式）时，下方出现「多实例审批方式」：

| 选项 | 实际含义 | 底层 |
|---|---|---|
| 无 | 普通单实例节点 | — |
| 会签（需所有人同意） | 所有人都要处理，全部通过才继续 | ParallelMultiInstance |
| 或签（一人同意即可） | 任一人处理即完成 | ParallelMultiInstance + 完成条件 |

配合「**顺序审批**」开关：

- **开启** = 依次轮流审批，此时该节点才会出现「会签回退」按钮的生效条件之一
- **关闭** = 并行会签，所有人同时收到任务

> 顺序会签的「会签回退」还需在授权功能里勾 `mulitiSequentialUnComplete`，两个条件都满足按钮才出现。

## 六、表单：设计、绑定与生效时机

业务表单基于 **vform3（`vform3-builds` 3.0.10）**，数据以 JSON 存放在 `wf_form.content`；表单类型字典为 `wf_process_form_type`（custom / system / external）。

### 6.1 画一张表单

`流程引擎 → 表单管理 → 新增`（填表单名称、表单编码、表单类型、表单分类）→ 列表点「**设计表单**」进 `/workflow/form/design`：

1. 从左侧控件库拖控件到画布（输入框、下拉、日期、附件等）
2. 右侧配置控件属性（字段名、必填、校验）
3. 点「保存表单」

> 保存后提示：**流程审批读取的是「部署时的表单快照」，本次修改需要重新部署流程后才对新实例生效。**

### 6.2 把表单绑到节点

`流程模型 → 设计`，选中节点（开始事件 / 用户任务），右侧「表单」页签的「**表单标识**」下拉里选表单 → 保存。

- 绑定结果是节点上的 `formKey`
- **开始事件必须绑定表单**：发起人就在这里填单
- 用户任务绑定表单后，审批弹窗会渲染该表单（回显 + 可编辑）

### 6.3 表单数据的流转

| 环节 | 存到哪 | 说明 |
|---|---|---|
| 部署流程时 | `wf_deploy_form.content` | **表单快照**，保证实例用的表单版本稳定 |
| 发起 / 审批提交时 | `wf_task_form.form_content` | 把表单 JSON 按「流程实例 + 节点」存一份 |

> ⚠️ **脚手架实现，不是推荐做法**：`wf_task_form` 是流程视角的通用表，`form_content` 是 JSON 文本，业务字段没有类型约束、无法建普通索引、难以 JOIN，数据也会按节点膨胀。
>
> **生产项目建议**：业务字段落各自的业务表（如 `sys_leave` / `sys_expense_report`），用普通列 + 索引；`wf_task_form` 只存 `proc_ins_id` / `task_id` / `activity_id` / `form_id` 这类流程元数据，业务表用 `proc_ins_id` 与流程软关联。
>
> ```sql
> -- ❌ 走 JSON 解析，无索引
> SELECT * FROM wf_task_form WHERE form_content::jsonb ->> 'status' = 'approved';
> -- ✅ 走业务表普通列
> SELECT * FROM sys_leave WHERE approval_status = 'approved';
> ```

**表单定义（`wf_form.content`）改了，快照不会自动更新**——必须重新部署流程，这是最容易踩的坑（见[第十二章](#十二常见问题排查)）。

### 6.4 表单模板与表单分类

| 功能 | 表 | 现状 |
|---|---|---|
| 表单模板 | `wf_form_template` | 接口 `/workflow/formTemplate/*` 已实现（列表、详情、保存、删除、预览），页面文件 `formTemplate/index.vue` 存在但**未挂菜单/路由** |
| 表单分类 | `wf_form_category` | 接口 `/system/category/*`（`workflow:systemCategory:*`）已实现，「表单管理」页的下拉在用；页面文件 `formCategory/index.vue` 同样未挂路由 |

## 八、审批操作详解

### 8.1 在哪里审批

| 入口 | 能做什么 |
|---|---|
| 我的待办列表 | 每行直接点审批按钮（按钮由**该行节点**的授权功能动态生成） |
| 流程详情页（带 `taskId`） | 左侧流程图 / 流程表单，右侧当前任务 + 审批按钮 + 审批记录时间线 |
| 待签收列表 | 候选任务先「签收」，再回待办办理 |

> 详情页只有**带 `taskId`** 进入时才显示审批按钮；看已结束的流程没有当前任务，也没有按钮，属正常。

### 8.2 各操作的区别（重点）

| 操作 | 流程会怎样 | 历史记录 | 典型场景 |
|---|---|---|---|
| **同意** | 流转到下一节点，可同时填意见、流程变量、业务表单、抄送人 | 保留 | 正常通过 |
| **驳回** | **直接结束整个流程**（执行实例被移到结束节点），状态标为 `reject` | 保留 | 一票否决 |
| **退回** | 退回到**指定节点**，流程继续流转（不是结束） | 保留 | 打回上一环节补材料 |
| **转办** | 任务转给他人，**处理完不再回到自己** | 保留 | 我不方便办，交给别人 |
| **委派** | 委派他人处理，**处理完回到自己确认** | 保留 | 我拿不准，请人先看 |
| **前加签** | 在当前节点**前**插入审批人（可多选）：被加签人先办，办完**回到操作人**，操作人再办一次才流转 | 保留 | 临时加一位领导先看 |
| **后加签** | 在当前节点**后**插入审批人：操作人的任务被引擎自动 complete，被加签人办完才流转 | 保留 | 办完再让某人过目 |
| **会签回退** | **仅顺序会签节点**：退到本节点上一位已处理的审核人重办 | 保留 | 会签顺序中发现问题 |
| **终止** | 结束整个流程（`processStatus` 置终止态） | 保留 | 流程作废但记录在案 |
| **撤回** | 发起人把流程撤回（`我的已发`），底层走 `RollbackCmd` 回滚 | 保留 | 发错了 |
| **跳过节点** | 由 `workflow:process:skipUserTask` 控制，跳过当前 / 指定节点 | 保留 | 特殊处理 |
| **变更处理人** | 直接改任务处理人（`editProcessTaskAssignee`） | 保留 | 原处理人离职 / 休假 |
| **废除** | 终止 + **物理删除**（历史、意见、扩展、抄送、表单全删） | **不保留** | 测试数据清理 |

> **前加签 vs 后加签**（小李在 A 节点被加签给张三）：
>
> | 时刻 | 前加签 | 后加签 |
> |---|---|---|
> | 点按钮后 | 小李的 A 任务**挂起**（assignee 清空） | 小李的 A 任务**被引擎自动 complete** |
> | 谁先看到待办 | 张三 | 张三（小李那份已没了） |
> | 张三办完后 | 小李的 A 任务**回来**，再办一次才流转 | 直接流转到下一节点 |
> | 适用 | 让专家先过一遍，自己再拍板 | 自己先表态，再让人把关 |

### 8.3 审批弹窗里有什么

| 区域 | 内容 | 说明 |
|---|---|---|
| 审批意见 / 原因 | 同意 / 驳回 / 退回 / 会签回退 / 终止时出现 | 写进 `act_hi_comment` + `wf_comment_info`；label 随动作变化（审批意见 / 驳回原因 / 退回原因 / 回退说明 / 终止原因） |
| 加签留言 | 前加签 / 后加签时出现，选填 | 写给被加签人的说明 |
| 接收人 / 加签人 | 转办、委派（单选）；前加签 / 后加签（多选） | — |
| 退回节点 | 仅「退回」，下拉列出可退回节点 | 后端只列「已办过且能到达当前节点」的节点 |
| 流程变量 | 同意 / 驳回时可填 **JSON** | 格式错误会直接提示 |
| 业务表单 | 节点绑定的表单 | 随任务提交保存到 `wf_task_form`（生产建议见 §6.3） |

### 8.4 抄送怎么发

节点授权功能勾了 `copy` 后，节点就「允许抄送」。抄送**随同意 / 驳回等动作一起提交**（没有独立按钮）：

- 抄送对象在「**抄送我的**」能看到该流程
- 可以点「抄送已读」标记已读（`readCopy`）

### 8.5 流程图上的颜色

流程图用 bpmn-js 渲染并按状态着色：

| 颜色 | 含义 |
|---|---|
| 🟠 橙色 | 当前待处理节点 |
| 🟢 绿色 | 已办节点 / 已走过的连线 |
| 🔴 红色 | 驳回节点 |

## 九、流程中心：终止、废除与清空

`流程中心`（`/workflow/center`）有三个页签：

| 页签 | 内容 |
|---|---|
| 未完结 | 引擎级「未完成」的实例（`running`） |
| 已完结 | 引擎级「已完成」的实例（`completed`） |
| 已终止 | 已完结但流程状态为终止 / 撤销的实例 |

列表支持按流程名称 / 流程标识 / 发起人 ID 查询，操作有「详情」「终止」「废除」，并支持批量。

| 操作 | 数据影响 | 可恢复 |
|---|---|---|
| **终止** | 只结束流程；历史、意见、表单快照、抄送**全部保留** | — |
| **废除** | 先终止，再**物理删除** Flowable 历史 + `wf_comment_info` + `tbl_flow_extend_procinst` + `wf_copy` + `wf_task_form` | ❌ 不可恢复 |
| **清空全部流程数据** | 比废除更彻底：连流程定义、部署、模型、分类、表单一起清掉（[§4.8](#48-流程数据清盘一键清空危险操作)） | ❌ 不可恢复 |

> 破坏力递增：**终止 < 废除 < 清空全部流程数据**。前两个作用于选中的实例，第三个是全局清盘。
> 注意：**流程替换（迁移）的最后一步会废除旧流程**，即旧实例的历史会被物理删除（意见已提前复制到新流程）。

流程状态取值（`ProcessStatus` 枚举）与界面文案：

| 值 | 界面文案 |
|---|---|
| `running` | 进行中 / 流转中 |
| `completed` | 已完结 / 已结束 |
| `reject` | 已驳回 |
| `return` | 已退回 |
| `canceled` | 已终止 / 已撤销 |
| `delete` | 已删除 |

## 十二、常见问题排查

### Q1：待办里点不到审批按钮 / 提示「当前节点未配置授权功能」

1. 节点「授权功能」是否勾选（设计器 → 点该用户任务 → 授权功能）；
2. 勾了之后**是否重新保存并部署**（不重新部署，运行中的实例仍用旧定义）；
3. 当前用户角色**是否有对应菜单权限**（第十章）；
4. 若只有「终止」没有其他按钮，说明授权功能整体为空。

### Q2：表单改了，审批时看到的还是旧的

**设计如此**：审批读的是 `wf_deploy_form.content`（部署时的快照）。
解决：`流程模型 → 设计 → 保存流程`（自动重新部署），**新发起**的实例才用新表单；已在跑的实例保持旧快照。

### Q3：模型列表里没有「发起」入口 / 测试启动页提示「暂无可启动的流程」

- 模型是否**已部署**？（状态 = 已部署）
- 是否被**挂起**？（已挂起不能发起新的）
- 模型是否至少有一个**开始事件**且流程合法？

### Q4：发起时报流程变量 JSON 错误

「流程变量」必须是**合法 JSON 对象**，例如 `{"days":5}`；`{days:5}` 缺引号会被拒。

### Q5：审批提交报「请先完善表单中的必填项」

节点绑定的业务表单里有必填字段没填。审批弹窗里的**业务表单**与上面的**审批意见**是两套独立数据，都要按要求填。

### Q6：审批同意了，但下一节点没人收到任务

- 下一节点**审批人配置为空**：可开启「为空跳过」或修正人员 / 表达式；
- 审批人用的是**候选人员**：任务进了「待签收」，需要候选人先签收；
- 用的是**表达式**：确认表达式引用的流程变量确实存在。

### Q7：能不能直接改数据库把流程挪到下一步？

**不要**。`act_ru_*` / `act_hi_*` 之间有一致性约束，手工改会导致流程图、审批意见、待办三者对不上。
正确做法：用界面提供的**退回 / 变更处理人 / 跳过节点 / 终止**。

### Q8：改了流程定义，正在跑的实例怎么办？

已经启动的实例**继续按原版本**走完，这是 Flowable 的标准行为。
如果必须让某个实例走新定义，用**流程迁移**（[§4.7](#47-流程替换运行中实例迁移到新流程定义)）。

### Q9：流程图打不开 / 显示「暂无流程图」

- 该模型**未部署**时无法预览流程图；
- 流程实例可能没有对应的 PNG / XML 资源（历史被清理过）；
- 看后端日志中 `ProcessViewer` / `WfProcessFlowViewerService` 相关异常。

### Q10：会签回退按钮不出现

两个条件缺一不可：节点是**顺序会签**（多实例 + 顺序审批开启）**且**授权功能里勾了「会签回退」。

### Q11：前加签 / 后加签 / 终止按钮不出现

这三个动作**已并入节点「授权功能」**：

1. 打开流程设计器，点对应用户任务节点；
2. 在右侧「授权功能」里**勾选**「前加签」「后加签」或「终止」；
3. **保存并部署**（只有新部署的模型生效）；
4. 还需要当前用户有对应菜单权限（`workflow:process:beforeAddSignTask` / `afterAddSignTask` / `workflow:process:cancel`）。

> 升级前的存量模型**不会自动多出这三个按钮**。

### Q12：后加签之后小李的待办没了，张三办完直接到下一节点

**预期行为**：后加签的语义是「小李先表态，张三再补审」。

| 时刻 | 小李 | 张三 |
|---|---|---|
| 后加签提交 | 当前 A 任务被引擎自动 complete | A 任务出现在张三待办 |
| 张三办完 | 无操作 | — |
| 流程流向 | A 节点结束，**直接流转到下一节点**（不回到小李） | — |

想要「张三办完再回到小李」，用**前加签**。

### Q13：清盘之后流程分类 / 表单 / 模型全没了？

清盘会清 `wf_category` / `wf_form` / `wf_form_*` / `flw_expression` 与全部部署模型（[§4.8](#48-流程数据清盘一键清空危险操作)）。按 §4.8.4 的顺序重建即可。

### Q14：跑过清盘后，演示数据（请假/报销表单）也不见了

正常：`wf_category` / `wf_form` 都在清盘范围内。需要演示数据时重新导入对应 SQL 段即可。

### Q15：迁移之后旧流程的历史查不到了

流程替换的最后一步是**废除旧流程**，而「废除」会**物理删除**旧实例的历史（`act_hi_*`）与业务表数据。历史意见已提前复制到新流程（带 `[从旧流程 xxx 复制]` 前缀）。如果需要保留旧流程历史，不要用迁移，改用「终止」后由业务侧自行处理。
